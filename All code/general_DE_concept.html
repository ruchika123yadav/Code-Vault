01

ETL vs ELT and transformation placement

The difference is where transformation happens, but the real interview question is how governance, compute, data sensitivity, and reuse affect that choice.

Interview-ready answer

ETL extracts data, transforms it before the analytical target, and then loads the result. ELT extracts and loads raw or lightly processed data first, then transforms it inside the target platform. I choose based on where scalable compute exists, whether raw data may enter the target, latency, transformation reuse, and governance requirements.

DecisionETL is stronger whenELT is stronger when
Data accessSensitive fields must be masked before landingGoverned raw storage is allowed
ComputeA dedicated transformation engine already existsThe warehouse/lakehouse has elastic compute
ReuseOnly a narrow curated target is neededMultiple teams may reuse raw history
ChangeSource and target contracts are stableBusiness logic changes frequently and raw replay is valuable

A practical hybrid

Most real systems are hybrid: validate transport-level structure and remove prohibited data before landing, preserve an immutable Bronze copy, then perform business transformations as ELT in a lakehouse or warehouse.

Is ELT always better for cloud platforms?

No. Cloud compute makes ELT attractive, but regulatory rules, network egress, target limitations, or the need to reject prohibited data before landing can require ETL or a hybrid design.

Where would you validate data in ELT?

I validate the ingestion contract before or during landing, retain rejected records with reason codes, and then run business-quality checks at each modeled layer. ELT changes transformation placement; it does not remove validation.

Practice drill

Take a customer source containing PII and design ETL, ELT, and hybrid versions. State exactly where masking, deduplication, and business rules execute, then choose one.

02

Batch vs streaming vs micro-batch

Latency is only one axis. Correct selection also considers event ordering, operational complexity, cost, traffic shape, and how quickly the business can act on data.

Interview-ready answer

Batch processes a bounded collection on a schedule. Streaming processes an unbounded sequence continuously. Micro-batch is a streaming implementation that repeatedly processes small bounded groups. I select the simplest model that meets the business action time, not the smallest technically possible latency.

ModelTypical fitMain trade-off
BatchDaily finance, periodic reconciliation, historical rebuildsSimple and cost-efficient, but freshness waits for the schedule
Micro-batchMinute-level dashboards and operational analyticsGood balance; latency includes trigger and processing time
Continuous streamingFraud signals, live monitoring, time-sensitive actionsLowest latency but more state, recovery, and capacity complexity
Latency decomposition

End-to-end latency is source delay + transport delay + queue wait + processing + sink commit + serving/refresh. Calling one component real time does not make the whole path real time.

Can a 15-minute triggered pipeline be called real time?

Usually it is near-real-time or micro-batch because records wait up to the trigger interval before processing. A separate continuously running event stream can still be real time while the 15-minute trigger handles batch reference data or maintenance.

When would you deliberately choose batch over streaming?

When the business only acts daily, the source arrives as files, exact reconciliation is easier in bounded runs, or streaming operating cost and complexity do not produce business value.

Practice drill

For an order dashboard, fraud alert, payroll report, and hourly inventory feed, define the freshness requirement and choose batch, micro-batch, or streaming. Include one cost and one recovery implication for each.

03

Full load, incremental load, CDC, and watermarks

Incremental ingestion is not one pattern. You must know which changes are visible, how progress is stored, and whether deletes can be reproduced.

Interview-ready answer

A full load reads the complete source. An incremental load reads only a changed subset. A watermark filters on a monotonic or last-modified column, while log-based CDC reads database change records and can preserve insert, update, and delete operations.

MethodCapturesKey risk
Full loadCurrent complete stateHigh source load and long windows
Increasing ID watermarkUsually insertsMisses updates and deletes
Updated timestamp watermarkInserts and updatesClock precision, ties, late commits, and deletes
Log-based CDCOrdered inserts, updates, deletesRetention, connector state, schema changes, and replay handling
Pseudo SQL - bounded watermark
-- Read a stable half-open range.
SELECT *
FROM source_orders
WHERE updated_at > :previous_watermark
  AND updated_at <= :new_high_watermark;

-- Advance state only after the target commit and reconciliation succeed.

Capture the new high watermark at the beginning of the run, read a bounded interval, write idempotently, reconcile, and only then commit progress. Use a composite boundary such as (updated_at, primary_key) when timestamps can tie.

Resume trap

A last-modified watermark is not full CDC if it cannot capture deletes. Say exactly which change types your design captures and how hard deletes are represented.

How do you avoid missing rows with the same timestamp?

Use a half-open interval plus a tie-breaker key, or overlap the read window and deduplicate by business key/version. The state must represent a deterministic ordered boundary.

When is a full load still reasonable?

For a small reference table, an unreliable source change column, an initial load, or a periodic reconciliation snapshot. Simplicity can be safer than fragile incremental logic at small scale.

Practice drill

Design a customer incremental load with inserts, updates, and hard deletes. Write the source predicate, state table fields, target merge rule, and a reconciliation query.

04

Idempotency, retries, checkpoints, and safe reruns

A reliable pipeline expects retries and repeated input. Its correctness cannot depend on a task running exactly once.

Interview-ready answer

An idempotent pipeline can process the same logical input more than once and still produce the same correct target state. I achieve this with stable input identity, deterministic transformations, transactional or atomic writes, and progress that is committed only after successful output.

Separate the concepts

ConceptPurposeExample
RetryRepeat transiently failed workExponential backoff for a throttled API
CheckpointRemember durable progress/stateLast committed source offset
Idempotent writeNeutralize duplicate executionMERGE by event ID and version
Atomic commitAvoid visible partial target stateTransaction or publish-by-pointer swap
Pseudo code - commit protocol
run_id = create_run(source_range)
input_rows = read_source(source_range)
result = deterministic_transform(input_rows)

begin_transaction()
merge_target(result, key="event_id", version="event_version")
write_audit(run_id, source_range, counts(result))
commit_transaction()

mark_source_range_committed(source_range)
Retry rule

Retry transient failures such as timeouts and throttling with bounded exponential backoff and jitter. Do not blindly retry deterministic failures such as an incompatible schema, invalid credentials, or a broken business rule.

Is overwrite always idempotent?

No. It is idempotent only when the replacement scope is exact, the rebuilt data is deterministic, and readers cannot observe a partial overwrite. A broad or non-atomic overwrite can delete valid data.

What if writing succeeds but checkpoint update fails?

The source range will be replayed, so the target write must tolerate duplicates. This is why checkpointing alone is not the idempotency mechanism.

Practice drill

Inject a failure after target write but before progress commit. Rerun the same range and prove row count, keys, aggregates, and audit status remain correct.

05

Backfills, replay, and recovery boundaries

A backfill is controlled historical recomputation. It needs an explicit range, isolated resources, deterministic logic, and a safe publication strategy.

Interview-ready answer

A backfill reprocesses a defined historical interval to repair missing data or apply corrected logic. I parameterize the interval, pin the code/config version, make writes idempotent, limit concurrency, reconcile each partition, and publish only validated output.

ScopeDates, entities, expected volume
->
RecomputeVersioned code and input snapshot
->
ValidateCounts, keys, totals, quality
->
PublishMerge or atomic partition replacement

Protect current production

  • Use a separate queue, cluster, or concurrency pool.
  • Prevent old versions from overwriting newer records.
  • Track backfill run ID and code version in audit metadata.
  • Pause downstream notifications until the range is consistent.
  • Define rollback as a table version or previous partition set.
Would you backfill directly into Gold?

Usually I replay from the earliest trusted retained layer and rebuild downstream deterministically. Writing only Gold can hide inconsistencies with Silver unless the repair is narrowly proven and audited.

How do you handle events updated after the historical range?

Use version-aware merge rules so the backfill cannot replace a newer target version, or rebuild into a shadow target and reconcile before switching consumers.

Practice drill

Plan a 90-day backfill after a tax-rule bug. Define source snapshot, partition range, parallelism cap, validation gates, publication, and rollback.

06

Late and out-of-order data

Event time and arrival time are different. A correct design states how long it waits, what happens after that boundary, and which outputs may change.

Interview-ready answer

Late data arrives after the time when it was expected, and out-of-order data arrives in a sequence different from event order. I process by event time, use stable event IDs and versions, define an allowed-lateness policy, retain replayable raw data, and specify how very late corrections reach downstream tables.

DecisionQuestionTypical answer
Event timestampWhich source field represents business occurrence?event_time, not ingestion time
Lateness budgetHow late is common and acceptable?Based on measured distribution and SLA
State cleanupWhen can windows/dedup state be removed?After watermark or retention boundary
Very late pathDrop, quarantine, or correction?Usually correction/replay for financial facts
Watermark misunderstanding

A watermark is not a promise that every older event is always dropped. It is an event-time progress boundary that lets a supported stateful operation finalize or clean old state; exact behavior depends on the operation and engine.

How do you choose watermark duration?

Measure the event-delay distribution, identify business correction requirements, estimate state cost, and choose a threshold that meets correctness while bounding state. Monitor late-beyond-threshold rate.

What if a late event changes an already published daily total?

Use an updatable sink or write a correction fact, recompute the affected partition/window, update the semantic layer, and audit the correction. Append-only final output is unsuitable if business values can change.

Practice drill

Create an event timeline with on-time, 10-minute-late, and two-day-late updates. Define the online policy, correction path, and three metrics that show whether the policy is adequate.

07

Schema drift, evolution, and data contracts

Schema drift is an observed change; schema evolution is the controlled response. A data contract makes compatibility and ownership explicit before production breaks.

Interview-ready answer

Schema drift is an unexpected or detected change in fields, types, or structure. Schema evolution is the governed process for accepting compatible changes and migrating incompatible ones. A data contract defines schema, semantics, keys, quality expectations, ownership, versioning, and change rules between producer and consumer.

ChangeCompatibilityResponse
Add nullable fieldUsually backward compatibleAccept, monitor adoption, update documentation
Remove/rename fieldBreaking for existing consumersDeprecate, dual-publish, version contract
Integer to stringPotentially breakingQuarantine or explicit migration
Meaning/unit changesBreaking even if type is sameNew field/version and consumer migration
YAML - compact data contract
dataset: orders
version: 2
owner: commerce-data
grain: one row per order version
keys: [order_id, version]
fields:
  order_id: {type: string, nullable: false}
  amount: {type: decimal(18,2), nullable: false, min: 0}
  updated_at: {type: timestamp_utc, nullable: false}
compatibility: backward
freshness_sla_minutes: 15
Why is automatic schema merge risky?

It can silently accept misspelled fields, unexpected types, or uncontrolled growth. I allow only approved compatible changes and alert or quarantine unknown breaking changes.

Schema validation passed. Is the data valid?

Not necessarily. Schema checks structure and types; business validity also needs allowed values, ranges, referential integrity, uniqueness, and semantic rules.

Practice drill

Version the order contract above after renaming amount to gross_amount and changing currency behavior. Design a migration that keeps two consumers working during the transition.

08

Data quality and source-to-target reconciliation

Quality must be measurable and tied to a business consequence. A single row-count check cannot prove data correctness.

Interview-ready answer

Data quality describes whether data is fit for its intended use. I measure completeness, validity, uniqueness, consistency, timeliness, and referential integrity at the correct grain. Reconciliation proves that source records and amounts are accounted for through valid, rejected, and intentionally filtered outcomes.

DimensionExample testMetric
CompletenessRequired customer ID is presentNon-null percentage
ValidityAmount is non-negative; status is allowedInvalid rows by rule
UniquenessOne current row per business keyDuplicate key count
ConsistencyOrder total equals line totalsMismatch count/value
TimelinessData available before SLAFreshness lag
SQL - reconciliation skeleton
SELECT run_id,
       source_count,
       valid_count,
       rejected_count,
       filtered_count,
       source_count - valid_count - rejected_count - filtered_count AS unexplained,
       source_amount - valid_amount - rejected_amount - filtered_amount AS amount_gap
FROM pipeline_audit
WHERE run_id = :run_id;
Defending a percentage

Do not say 90% data integrity unless the numerator, denominator, covered rules, measurement period, and threshold are documented. A defensible example is: 99.7% of 8.2 million daily rows passed six agreed critical rules over 30 days.

When should a quality failure stop the pipeline?

Stop for contract-breaking or critical correctness failures, such as missing primary keys or material reconciliation gaps. Quarantine known record-level defects when the valid subset remains useful and the invalid-rate threshold is not exceeded.

Why compare aggregates as well as counts?

Equal counts can still hide changed amounts, duplicate-and-missing pairs, or field corruption. Compare keys, totals, min/max, nulls, and business-specific checksums by a useful partition.

Practice drill

Create a reconciliation table for orders with source, valid, rejected, duplicate, and filtered outcomes. Add row-count, distinct-key, amount, and freshness checks with pass/fail thresholds.

09

Observability, SLAs, SLOs, lineage, and triage

Monitoring tells you that a known condition happened. Observability gives enough evidence to understand unfamiliar failures across the pipeline.

Interview-ready answer

Pipeline observability combines logs, metrics, traces/run context, data-quality signals, and lineage so operators can detect, diagnose, and recover failures. An SLA is the external commitment; an SLO is the internal measurable target used to protect that commitment.

Minimum telemetry per run

  • Run ID, code/config version, source range, start/end, status.
  • Rows and bytes read, written, rejected, inserted, updated, deleted.
  • Freshness lag, duration, throughput, retries, and queue delay.
  • Quality-rule results and source-to-target reconciliation.
  • Input/output dataset lineage and downstream impact.
  • Error category, owner, runbook link, and correlation ID.
JSON log - structured event
{
  "event": "pipeline_run_failed",
  "pipeline": "orders_silver",
  "run_id": "2026-07-23T02:00Z",
  "source_range": "offsets:10420-11890",
  "error_class": "schema_incompatible",
  "invalid_rate": 0.37,
  "owner": "commerce-data"
}
What would you alert on?

Alert on symptoms that need action: missed freshness SLO, sustained consumer lag, critical quality failure, unexplained reconciliation gap, repeated retries, or abnormal duration. Avoid paging on every isolated log line.

How does lineage help during an incident?

It identifies which upstream change introduced the issue and which downstream datasets, dashboards, or teams may be affected, reducing diagnosis and communication time.

Practice drill

Define an SLO and alert set for a pipeline due every 15 minutes. Include warning/critical thresholds, owner, runbook action, and a no-data alert.

10

At-most-once, at-least-once, and exactly-once

Delivery semantics describe outcomes across failure and retry. End-to-end exactly-once is a property of the complete source-processing-sink protocol.

Interview-ready answer

At-most-once may lose records but does not redeliver them. At-least-once avoids loss by retrying but may create duplicates. Exactly-once means each logical event affects the final result once, which normally requires replayable input, durable progress, deterministic processing, and an idempotent or transactional sink.

GuaranteeOn failureSuitable example
At-most-onceProgress can advance before processing; loss is possibleNoncritical telemetry sampling
At-least-onceProcess then acknowledge; redelivery is possibleMost event pipelines with deduplication
Exactly-once effectRetry is neutralized at target stateFinancial balance update keyed by event ID
Language precision

A broker, framework, or sink may provide a local guarantee, but a side effect such as an email or external API call can still happen twice. State the guarantee boundary.

How do you turn at-least-once delivery into exactly-once business effect?

Give each event a stable ID, persist processed IDs or merge by ID/version in the same transactional boundary as the state update, and acknowledge source progress only after that commit.

Is deduplication forever practical?

Usually no. State retention should match the maximum replay/duplicate horizon, or the target should enforce a durable uniqueness constraint. State cost is part of the guarantee.

Practice drill

Draw failure points between broker read, transformation, target write, and offset commit. For each failure, state whether a record can be lost or duplicated and how your design responds.

11

Data lake vs warehouse vs lakehouse

These are architectural patterns, not quality rankings. The right answer depends on data types, governance, transactions, BI performance, and team operating model.

Interview-ready answer

A data lake stores large volumes of structured and unstructured data in open files, often with schema applied when read. A warehouse stores governed, modeled analytical data with strong SQL serving. A lakehouse adds table reliability, governance, and warehouse-like operations on lake storage.

PlatformStrengthWatch-out
LakeLow-cost flexible storage, raw history, ML and file interoperabilityCan become hard to trust without catalog, contracts, and table management
WarehouseConsistent SQL, dimensional serving, concurrency, mature BIRaw/semi-structured flexibility and duplicated storage may be concerns
LakehouseOpen files plus ACID tables, batch/stream unification, multiple workloadsStill needs governance, optimization, and workload isolation
Does a lakehouse remove the need for a warehouse?

No. A warehouse may still be the best governed serving layer for predictable BI concurrency and dimensional SQL. Some organizations use a lakehouse for engineering and a warehouse or SQL endpoint for serving.

What makes a data lake become a data swamp?

Missing ownership, catalog, schema contracts, lineage, retention, access controls, quality checks, and discoverable curated layers. The storage technology is not the main failure.

Practice drill

Choose a target architecture for raw IoT JSON, governed finance reporting, data science features, and 500 concurrent BI users. Explain which data is copied and which is queried in place.

12

CSV, JSON, Avro, Parquet, and Delta

A file or table format should match transport, schema evolution, query pattern, and mutation requirements.

Interview-ready answer

CSV and JSON are text formats useful for interchange and debugging. Avro is a row-oriented binary format with an explicit schema, useful for event transport. Parquet is a columnar analytical file format. Delta is a table format that uses data files plus a transaction log for reliable table operations.

FormatBest fitMain limitation
CSVSimple flat exchangeWeak types, escaping ambiguity, poor analytics efficiency
JSONAPIs, nested payloads, human inspectionVerbose and costly to scan at scale
AvroCompact row records and schema-based event exchangeLess suitable than columnar formats for selective analytics
ParquetLarge analytical scans with projection and filtersFiles alone do not provide transactions or table history
DeltaMutable/reliable lakehouse tables, merge, time travelTransaction-log maintenance and engine compatibility matter

Why columnar matters

If a query reads three columns from a 100-column table, a columnar reader can avoid most unrelated column data. Similar values are stored together, which also improves encoding and compression.

Why not use Parquet directly for every event message?

Parquet is optimized for analytical batches, not individual low-latency messages. Avro or JSON is easier for record transport; compact those records into Parquet/Delta for analytics.

Delta vs Parquet in one sentence?

Parquet defines how columnar data is stored in files; Delta adds table-level transaction metadata and operations around those data files.

Practice drill

Write the same sample dataset as CSV, JSON, and Parquet. Compare file size, inferred schema, projected-column read, and behavior after adding a nullable field.

13

Partitioning, pruning, compression, and small files

Good physical design reduces data read without creating excessive directories, metadata, or tiny tasks.

Interview-ready answer

Partitioning physically groups data by selected columns, while partition pruning skips groups that cannot satisfy a filter. A good partition column appears in common filters, has manageable cardinality, distributes data reasonably, and creates useful file sizes.

ChoiceGood exampleBad example
Partition keyevent_date for time-filtered eventsUnique order_id
GranularityDay for moderate daily volumeMinute with only a few rows per minute
File sizeLarge enough for efficient scans and parallelismThousands of tiny files per partition
CompressionSplittable codec matched to format/engineMaximum compression that makes CPU the bottleneck

Small-file problem

Many tiny files increase listing, metadata, planning, open, and task-scheduling overhead. Fix the cause by controlling write parallelism and trigger size, then compact historical small files. Compaction changes physical layout, not logical rows.

Partition myth

More partitions do not automatically mean more speed. Too few create large slow tasks; too many create scheduler and metadata overhead. Measure input size, task duration, pruning, and target file sizes.

Partitioning vs bucketing/clustering?

Partitioning creates coarse directory or table partitions that can be pruned. Bucketing or clustering organizes data within/across files to improve joins or selective filtering without one directory per high-cardinality value.

What is Z-Ordering at interview depth?

It colocates related column values across files to improve data skipping for filters on selected columns. It is not the same as table partitioning and should be chosen from actual query patterns.

Practice drill

Given 2 TB per month of orders queried by date, country, and customer ID, choose partition columns and compaction cadence. Explain why customer ID should not be a folder partition.

14

OLTP, OLAP, normalization, and denormalization

Operational and analytical systems optimize for different access patterns. Modeling should follow workload, not a blanket rule that normalized or denormalized is better.

Interview-ready answer

OLTP systems handle many small concurrent transactions and usually use normalized models to reduce update anomalies. OLAP systems scan and aggregate large histories and often use dimensional or denormalized models to simplify queries and improve analytical performance.

PropertyOLTPOLAP
WorkloadPoint reads/writes, short transactionsScans, joins, aggregates
DataCurrent operational stateHistorical integrated data
ModelOften 3NF normalizedOften star/dimensional
OptimizationWrite integrity and concurrencyRead simplicity and throughput
Normalization answer

1NF makes values atomic, 2NF removes partial dependency on part of a composite key, 3NF removes transitive dependency on non-key columns, and BCNF requires every determinant to be a candidate key.

Why not run all BI queries on the production OLTP database?

Large scans and joins can compete with customer transactions, the schema is harder for analytics, history may be overwritten, and cross-source integration is limited.

Does denormalization mean duplicating everything?

No. It deliberately stores selected redundancy to support known reads, with controlled refresh and consistency. Grain and ownership still need to be explicit.

Practice drill

Convert a normalized order/customer/product schema into an analytical star. Name the fact grain, dimensions, keys, and which operational attributes should not be copied.

Grain, facts, dimensions, and keys

Declaring grain is the most important dimensional-modeling step because it determines what one fact row represents and which dimensions and measures are valid.

Interview-ready answer

A fact table stores measurements at a declared business-process grain, and dimensions provide descriptive context for those measurements. The grain is the exact meaning of one fact row. A natural key comes from the source business; a surrogate key is a warehouse-generated identifier used to integrate history and sources.

Four-step model

  1. Select the business process.
  2. Declare the atomic grain in one sentence.
  3. Identify dimensions valid at that grain.
  4. Identify facts and their aggregation behavior.
Measure typeMeaningExample
AdditiveCan sum across all dimensionsLine revenue
Semi-additiveCan sum across some dimensions, not timeAccount balance snapshot
Non-additiveShould not be summedPercentage or unit price
Mixed-grain trap

Do not store order-level shipping amount on every order-line row and then sum it. Either allocate it using a documented rule or place it in a fact at the correct grain.

Why use surrogate keys in dimensions?

They separate warehouse identity from changing source keys, support multiple sources and SCD history, and let a fact point to the correct historical dimension version.

What is a conformed dimension?

A consistently defined dimension shared across business processes, such as Date or Customer, so facts can be compared with the same keys and attributes.

Practice drill

For a food-delivery system, declare grains for order, order line, delivery event, and daily courier snapshot. List dimensions and additive behavior for each.

16

Star, snowflake, fact types, and advanced dimensions

Interviewers often test whether you can model a process beyond a basic transaction fact and simple dimensions.

Interview-ready answer

A star schema keeps dimensions relatively denormalized around facts for simple and fast analytics. A snowflake normalizes dimension hierarchies, reducing some redundancy but adding joins and user complexity.

PatternOne row meansExample
Transaction factOne business eventOne order line
Periodic snapshotState for an entity at a regular intervalDaily account balance
Accumulating snapshotLifecycle instance updated across milestonesOrder placed, packed, shipped, delivered
Factless factAn event/coverage relationship without numeric measureStudent attendance

Useful dimension patterns

  • Degenerate dimension: a business identifier such as order number stored in the fact without its own descriptive table.
  • Role-playing dimension: one Date dimension used as order date, ship date, and delivery date.
  • Bridge table: resolves a many-to-many relationship, often with allocation rules.
  • Junk dimension: combines low-cardinality flags into one dimension.
Star vs snowflake: which is always faster?

Neither universally. A star often needs fewer joins and is easier for BI, but actual performance depends on engine, data size, caching, and query pattern. Snowflaking can help govern large reusable hierarchies.

Can an accumulating snapshot receive updates?

Yes. It intentionally updates milestone dates and durations as one process instance moves through its lifecycle, unlike an immutable transaction fact.

Practice drill

Model a hiring process using an accumulating snapshot, interview events using a transaction fact, and daily open-requisition counts using a periodic snapshot.

SCD Type 1, Type 2, and late-arriving dimensions

Slowly changing dimensions define how descriptive history is preserved and how facts find the correct dimension version.

Interview-ready answer

SCD Type 1 overwrites an attribute and does not preserve its old value. SCD Type 2 expires the current row and inserts a new version with effective dates and a current flag. Facts should use the dimension version effective at the business event time.

SQL - Type 2 lookup condition
SELECT d.customer_sk
FROM dim_customer d
WHERE d.customer_id = :customer_id
  AND :event_time >= d.effective_from
  AND :event_time <  d.effective_to;
CaseType 1Type 2
Correct spelling mistakeUsually appropriateUsually unnecessary
Customer segment historyLoses old segmentPreserves analytical history
Storage/query costLower/simplerMore rows and temporal logic
Late-arriving dimension

If a fact arrives before its dimension, use an inferred member with the natural key and unknown attributes, load the fact against that surrogate key, then update the inferred dimension when details arrive. Avoid changing the surrogate key if facts already reference it.

What sequence column should drive Type 2 changes?

Use a trustworthy source version, commit sequence, or event timestamp plus deterministic tie-breaker. Ingestion time is only a fallback because delayed events can arrive out of order.

Why use an exclusive effective_to boundary?

Half-open intervals such as [effective_from, effective_to) avoid overlap at exact boundary timestamps and make temporal joins unambiguous.

Kafka producers, brokers, topics, and partitions

Kafka scales an ordered log by partitioning it. Ordering is per partition, and the partition-key decision is both a correctness and load-distribution choice.

Interview-ready answer

A producer publishes records to a topic hosted by brokers. A topic is split into partitions, each an ordered append-only log. Consumers read records by offset, and a consumer group divides partitions among its members.

ProducerKey + value + headers
->
Topic partitionsOrdered logs on brokers
->
Consumer groupOne member per assigned partition

Partition-key reasoning

Use a key such as order_id when all events for one order must remain ordered. A null/random key distributes load but loses entity ordering. A hot key can create one overloaded partition, so profile cardinality and traffic skew.

Can Kafka guarantee global topic order?

Not across multiple partitions. It preserves order within each partition. Global order requires one partition or downstream sequence reconciliation, both with scalability trade-offs.

Can consumers in one group exceed the partition count?

They can exist, but extra consumers have no partition assignment, so active parallelism is bounded by the number of partitions.

Kafka offsets, groups, rebalancing, acks, and retention

A consumer's correctness depends on the relationship among processing, target commit, and offset commit. Broker retention is not the same as consumer progress.

Interview-ready answer

An offset identifies a record position within a partition. A consumer group stores its progress and shares partition ownership. Rebalancing changes assignments when membership or partitions change, so processing must safely handle revocation and replay.

Producer acksMeaningTrade-off
0Do not wait for broker acknowledgementLowest assurance
1Leader acknowledgesLeader failure can still lose unreplicated data
allAll required in-sync replicas acknowledgeStronger durability with latency/availability trade-off

Safe consumer sequence

  1. Read records from assigned partitions.
  2. Transform deterministically.
  3. Commit target output idempotently or transactionally.
  4. Commit offsets only for successfully durable output.
Retention trap

Kafka retention controls how long broker log segments remain, independent of whether a consumer has read them. A consumer lagging beyond retention can lose the ability to replay old offsets.

What happens if offset is committed before target write?

A crash can skip the record after restart, producing at-most-once behavior and data loss. Committing after the write gives at-least-once behavior, so the sink must handle replay.

Why can rebalancing cause duplicate work?

A consumer may process records but lose its partition before committing the corresponding offsets. The next owner resumes from the last committed offset and repeats those records.

Kafka vs Event Hubs and Schema Registry

The generic concept is a partitioned event log; the platform decision includes ecosystem, operations, protocol compatibility, integration, governance, and cost.

Interview-ready answer

Kafka is an open-source distributed event-streaming platform that can be self-managed or consumed as a managed service. Azure Event Hubs is a managed Azure event-ingestion service with Kafka protocol compatibility. I compare operational ownership, Azure integration, feature requirements, throughput model, networking, and total cost.

Decision areaKafkaEvent Hubs

CapacityPartitions, broker resources, provider modelPartitions plus service throughput/capacity model

Schema Registry and contracts

A registry stores versioned schemas and compatibility rules; it does not fix semantic changes automatically. Producers still own safe evolution, and consumers must define which versions they support.

If Event Hubs supports the Kafka protocol, is it identical to Kafka?

No. It enables many Kafka clients and patterns, but service operations, quotas, feature support, security, and pricing remain Event Hubs-specific. Validate required APIs and semantics.

Backward vs forward compatibility?

Backward compatibility means a new reader can read old data. Forward compatibility means an old reader can read data written by a new writer. Full compatibility requires both.

Orchestration, DAGs, schedules, and Airflow

An orchestrator coordinates work; it should not hide business logic inside one giant task or replace a processing engine.

Interview-ready answer

A DAG represents tasks and their dependencies without cycles. An orchestrator schedules runs, passes parameters, tracks state, applies retries, and exposes logs and alerts. I keep tasks idempotent and choose boundaries that can be retried independently without creating inconsistent output.

Python - Airflow-style DAG
from datetime import datetime, timedelta
from airflow.decorators import dag, task

@dag(
    schedule="0 * * * *",
    start_date=datetime(2026, 1, 1),
    catchup=False,
    default_args={"retries": 3, "retry_delay": timedelta(minutes=2)},
)
def hourly_orders():
    @task
    def extract(interval_start: str, interval_end: str):
        return {"start": interval_start, "end": interval_end}

    @task
    def transform(window: dict):
        return run_idempotent_transform(window)

    @task
    def reconcile(result: dict):
        assert_reconciliation(result)

    reconcile(transform(extract("{{ data_interval_start }}", "{{ data_interval_end }}")))

hourly_orders()

Scheduling terms

  • Logical/data interval: the time range a run represents, not simply wall-clock start time.
  • Catchup: creating missed historical intervals when enabled.
  • Backfill: deliberately creating runs for a bounded past range.
  • Dependency: a true data/control requirement, not a visual preference.
XCom/message trap

Pass references and small metadata between tasks, not large datasets. Store data in the processing/storage layer and let the orchestrator coordinate it.

How do you choose task boundaries?

Use independently observable and retryable units with durable handoffs, such as ingest, transform, quality gate, and publish. Avoid both one giant opaque task and thousands of tiny orchestration calls.

Should every failure be retried?

No. Retry transient infrastructure errors. Fail fast and alert on contract errors, invalid credentials, deterministic code bugs, or quality failures that require intervention.

Governance, security, PII, lineage, and retention

Security protects access; governance establishes ownership, meaning, policy, discoverability, and evidence across the data lifecycle.

Interview-ready answer

Data governance defines who owns data, what it means, who may use it, how quality is measured, and how long it is retained. Security enforces controls such as identity, least privilege, encryption, network boundaries, masking, and auditing.

ControlPurposeEvidence
Least privilegeOnly required actions on required dataRole grants and access reviews
Secret managementNo credentials in code/config/logsVault references and rotation logs
EncryptionProtect data in transit and at restTLS and key policy
PII masking/tokenizationLimit exposure while enabling useColumn policy and test results
AuditShow who accessed or changed whatImmutable access/change logs
Retention/deletionKeep data only as requiredPolicy, lifecycle jobs, deletion proof
Layered access

Raw/Bronze is not automatically open. It often contains the most sensitive and least cleaned data, so access should be narrower than curated aggregates.

Masking vs encryption?

Encryption protects bytes using keys, mainly at rest or in transit. Masking changes what an authorized query/user can see. They solve different threats and are often both required.

How does right-to-delete affect a lakehouse?

Locate the subject through catalog/lineage, remove or irreversibly anonymize governed copies, propagate to derived tables/caches, respect legal exceptions, and record auditable completion. Immutable backups need a documented expiration strategy.

Cost, performance, scaling, and workload isolation

Performance tuning should start with workload evidence and data scanned, not with permanently increasing compute.

Interview-ready answer

I optimize a data platform by measuring the critical workload, reducing unnecessary data movement and scans, choosing suitable physical design, and then sizing compute. I separate workloads so ingestion, backfills, and BI concurrency cannot starve each other.

Practical sequence

  1. Define SLO and identify the actual bottleneck.
  2. Remove unnecessary columns, rows, shuffles, and repeated work.
  3. Improve file sizes, partitions, statistics, and join strategy.
  4. Cache only reused expensive results.
  5. Scale compute with bounds, timeout, and cost attribution.
  6. Re-measure p50/p95 runtime, throughput, spill, and cost per unit.
WorkloadIsolation methodReason
Interactive BIDedicated SQL/serving computePredictable concurrency and latency
Scheduled ETLJob compute/queueElastic capacity and clean ownership
BackfillSeparate low-priority poolProtect current SLA
StreamingStable reserved baselineAvoid restart and lag from aggressive scale-down
When is autoscaling harmful?

When startup/scaling lag exceeds the workload window, stateful streaming needs stable capacity, limits are too high, or poor queries simply consume more resources. Use min/max bounds and monitor cost plus queue time.

When should you cache?

When the same expensive deterministic intermediate result is reused enough to repay materialization and storage cost. Do not cache one-use data or data too large for the storage level.

DataOps, CI/CD, promotion, and rollback

Deploying data code safely also means protecting contracts, historical state, schema, and partially processed ranges.

Interview-ready answer

Data CI/CD moves versioned code and configuration through automated tests, artifact creation, controlled environment promotion, deployment, verification, and rollback. The same artifact should be promoted; environment-specific endpoints and secrets are injected securely.

Test pyramid for pipelines

  • Contract tests for schema and compatibility.
  • Integration tests for storage, permissions, checkpoints, and target writes.
  • Data-quality tests on a representative controlled sample.

Old code may not understand a newly changed schema or checkpoint. A rollback plan states whether output/table version, state, migration, and downstream consumers must also be restored.

It proves that the tested bits are the deployed bits. Rebuilding can introduce dependency or packaging differences between test and production.

Test initial load, no-change run, insert, update, delete, tied watermark, late arrival, duplicate input, partial failure, replay, schema change, and reconciliation.

System design gate: reliable streaming platform

A strong streaming design makes ordering, lag, state, late data, replay, sink semantics, and operational capacity explicit.

Scenario

Design a near-real-time order-event platform for dashboards and fraud features. Peak rate is 80,000 events per second, events can arrive two hours late, and corrections must reach serving tables.

Interview-ready answer

I would key the event log by order ID for per-order ordering, use a versioned contract, retain enough broker history for recovery, checkpoint source progress, preserve raw events, deduplicate by event ID/version, and use event-time state with a measured lateness boundary. The sink must upsert corrections idempotently, while consumer lag, invalid rate, state size, and freshness are monitored.

Estimate peak throughput per partition, required consumer parallelism, key distribution, future growth, and service limits. More partitions increase parallelism but also coordination, files, and ordering scope.

Incident method, rapid Q&A, and revision gate

The final skill is staying structured under pressure: protect correctness first, restore service deliberately, and communicate evidence rather than guesses.

Incident response sequence

  1. Detect and scope: which runs, partitions, tables, and consumers are affected?
  2. Contain: stop bad publication, preserve evidence, and protect downstream users.
  3. Diagnose: compare first failing run, deployment, schema, source, capacity, and permissions.
  4. Recover: rollback or repair from a known boundary; reconcile before reopening.
  5. Prevent: root cause, missing control, owner, due date, and runbook/test update.
