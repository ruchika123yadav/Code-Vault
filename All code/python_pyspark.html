Python collections and complexity

Choose a collection from the operations you need, not from habit. Interviewers often test whether you understand membership, ordering, mutability, and duplicate behavior.

Interview-ready answer

Python provides four common built-in collections. A list is ordered and mutable, a tuple is ordered and immutable, a set stores unique hashable values and gives fast membership checks, and a dictionary stores key-value pairs with fast average lookup by key.

TypeOrderedMutableDuplicatesBest use
listYesYesYesSequence that changes
tupleYesNoYesFixed record or safe return value
setNo positional accessYesNoMembership and deduplication
dictInsertion order is preservedYesKeys are uniqueLookup, grouping, counting

Append / insert keyO(1) amortized appendO(1)Occasional resize makes list append amortized
Insert at frontO(n)Not applicableExisting list elements must shift

Python
records = [
    {"id": 101, "status": "ok"},
    {"id": 102, "status": "failed"},
    {"id": 101, "status": "ok"},
]

# Set: fast uniqueness and membership
unique_ids = {row["id"] for row in records}
if 102 in unique_ids:
    print("Record 102 exists")

# Dict: group or count by key
status_count = {}
for row in records:
    status = row["status"]
    status_count[status] = status_count.get(status, 0) + 1

print(unique_ids)       # {101, 102}
print(status_count)     # {'ok': 2, 'failed': 1}
Common mistakes
  • Using a list for repeated membership checks creates unnecessary O(n) scans.
  • Using a mutable object such as a list as a dictionary key fails because dictionary keys must be hashable.
  • Assuming a set has stable positional order. Use sorting when deterministic output matters.
  • Removing duplicates with set loses the original order unless you use an order-preserving pattern.
Python - ordered deduplication
values = [3, 1, 3, 2, 1]
deduplicated = list(dict.fromkeys(values))
print(deduplicated)  # [3, 1, 2]
Why is dictionary lookup usually O(1), and can it become O(n)?

A dictionary uses the key's hash to locate a bucket, so average lookup is O(1). In the theoretical worst case, many collisions can force more work and approach O(n). Resizing also has a cost, but it is spread across insertions.

When would you use a tuple instead of a list in a data pipeline?

Use a tuple for a small record whose shape should not change, such as (source_name, row_count), or for a hashable composite key. Use a list when elements must be added, removed, or replaced.

Strings, slicing, and frequency maps

Strings appear in file parsing, log processing, data cleaning, and coding rounds. The high-value patterns are normalization, splitting, joining, slicing, and counting.

Interview-ready answer

A Python string is an immutable sequence of Unicode characters. Immutable means an operation such as lower() or replace() returns a new string; it does not change the original object.

Python
raw = "  Order-101,PAID  "
clean = raw.strip().lower()
order_id, status = clean.split(",")
prefix, number = order_id.split("-", maxsplit=1)

print(prefix)           # order
print(number)           # 101
print(status)           # paid
print(clean[:5])        # order
print(clean[::-1])      # reverse

Frequency-map pattern

Python
from collections import Counter

events = ["click", "view", "click", "purchase", "view", "click"]

manual = {}

Pattern recognition

Words such as frequency, count each, first non-repeating, anagram, or duplicate usually point to a dictionary or Counter.

CSV trap

line.split(',') is not a real CSV parser. A field may contain a comma inside quotes. Use Python's csv module or Pandas/Spark for production files.

Why are strings immutable, and why does it matter?

Immutability makes strings safe to share and hash, so they can be dictionary keys. It also means repeated concatenation in a loop can create many temporary objects; collect pieces and use join for larger workloads.

Functions, scope, comprehensions, and sorting

Good data code is built from small, testable functions. Interviews often combine function design with transformations, filtering, and custom sorting.

Interview-ready answer

A function packages reusable behavior behind a clear input-output contract. Positional parameters map by position, keyword parameters map by name, *args collects extra positional arguments, and **kwargs collects extra keyword arguments.

Python
def normalize_record(record, required_fields=("id",), **defaults):
    """Return a cleaned copy without mutating the input."""
    cleaned = {key: value for key, value in record.items() if value is not None}

    for key, value in defaults.items():
        cleaned.setdefault(key, value)

    missing = [field for field in required_fields if field not in cleaned]
    if missing:
        raise ValueError(f"Missing required fields: {missing}")

    return cleaned

row = normalize_record({"id": 10, "country": None}, source="api")

Scope: LEGB

Python resolves a name in this order: Local, Enclosing, Global, then Built-in. Prefer passing values into functions instead of reading or changing global state.

Mutable default argument

Do not write def add(item, bucket=[]). That list is created once and reused across calls. Use None, then create a new list inside the function.

Python
def add_item(item, bucket=None):
    if bucket is None:
        bucket = []
    bucket.append(item)
    return bucket

Comprehension vs map/filter

Both are valid, but a comprehension is often easier to read when the transformation is short. Use a normal loop when validation, logging, exception handling, or multiple steps are required.

What is the difference between *args and **kwargs?

*args is a tuple of extra positional arguments. **kwargs is a dictionary of extra named arguments. They add flexibility, but explicit parameters are better when the contract is known.

When should you avoid a list comprehension?

Avoid it when the logic has multiple branches, side effects, complex error handling, or becomes difficult to scan. Readability matters more than reducing line count.

Iterators, generators, and memory

A generator lets a pipeline process one item at a time. This matters when a file or API result is too large to load into memory at once.

Interview-ready answer

An iterable can produce an iterator, and an iterator returns one item at a time through next(). A generator is a convenient iterator created by a function that uses yield. It is lazy, so values are produced only when requested.

Iterableiter(source)
->
Iteratornext(iterator)
->
One valueState is paused
->
Next valueState resumes
Python
import json
from pathlib import Path

def read_json_lines(path):
    with Path(path).open("r", encoding="utf-8") as file:
        for line_number, line in enumerate(file, start=1):
            if not line.strip():
                continue
            try:
                yield json.loads(line)
            except json.JSONDecodeError as exc:
                raise ValueError(f"Invalid JSON on line {line_number}") from exc

for record in read_json_lines("events.jsonl"):
    process(record)  # only one record must be active here
ListGenerator
Computes and stores all valuesComputes values on demand
Can be indexed and reusedNormally consumed once; no indexing
Good for small reusable resultsGood for large streams and pipelines
Memory grows with result sizeMemory stays closer to one item or batch
Generator traps
  • A generator body does not run when the generator object is created; it runs during iteration.
  • After it is exhausted, iterate again only by creating a new generator.
  • A generator does not automatically make the entire pipeline memory efficient if a later step calls list() or sorts all rows.
Generator vs iterator: are they the same?

Every generator is an iterator, but not every iterator is a generator. You can create an iterator with a class implementing __iter__ and __next__; a generator gives the same protocol through simpler yield syntax.

Files, CSV, JSON, pathlib, and context managers

Reliable ingestion starts with correct resource handling, explicit encoding, schema awareness, and validation instead of optimistic parsing.

Interview-ready answer

A context manager controls setup and cleanup around a block. For files, with guarantees that the file is closed even when parsing raises an exception. pathlib.Path gives an object-oriented and operating-system-safe way to work with paths.

Python - CSV
import csv
from pathlib import Path

def read_orders(path):
    with Path(path).open("r", encoding="utf-8", newline="") as file:
        reader = csv.DictReader(file)
        required = {"order_id", "amount", "event_time"}

        if not required.issubset(reader.fieldnames or []):
            raise ValueError(f"Missing columns: {required - set(reader.fieldnames or [])}")

        for row in reader:
            yield {
                "order_id": int(row["order_id"]),
                "amount": float(row["amount"]),
                "event_time": row["event_time"],
            }
Python - JSON
import json
from pathlib import Path

source = Path("input/orders.json")
target = Path("output/orders_clean.json")

Validation checklist

  • Check file existence and expected extension.
  • Use explicit text encoding.
  • Validate header or required keys before processing.
  • Convert data types with clear error handling.
  • Track input, valid, invalid, and output row counts.
  • Write to a temporary/staging target before publishing when partial output is unsafe.
Common mistakes
  • Using json.load for a JSON Lines file.
  • Reading a huge file with read() when line or batch processing is possible.
  • Using string concatenation for paths instead of Path.
  • Silently skipping malformed rows without a reject record and count.
Why pass newline='' when opening CSV files?

The csv module expects to manage newline handling itself. Using newline="" avoids unwanted blank rows and preserves CSV rules consistently across operating systems.

Exceptions, custom errors, and logging

A production data job must fail clearly, preserve the root cause, record useful context, and distinguish retryable failures from bad data.

Interview-ready answer

An exception represents an abnormal condition that interrupts normal control flow. Catch only exceptions you can handle meaningfully, add context, and either recover or raise again. Logging creates timestamped, leveled records that operations teams can search and alert on.

The reliable handling pattern

Python
import logging

logger = logging.getLogger(__name__)

class DataValidationError(ValueError):
    """Raised when a record violates the expected data contract."""

def parse_amount(record):
    try:
        amount = float(record["amount"])
    except KeyError as exc:
        raise DataValidationError("amount is required") from exc
    except (TypeError, ValueError) as exc:
        raise DataValidationError(f"invalid amount: {record.get('amount')!r}") from exc

    if amount < 0:
        raise DataValidationError("amount cannot be negative")
    return amount

try:
    amount = parse_amount({"id": 10, "amount": "bad"})
except DataValidationError:
    logger.exception("Record validation failed", extra={"record_id": 10})
    raise

finallyAlways runsUseful for cleanup not already handled by a context manager

  • Using print as production logging loses levels, timestamps, structure, and routing.
  • Retrying validation errors wastes time; only transient failures should normally be retried.
Why create a custom exception?

A custom exception gives a business or pipeline meaning to a failure. Callers can handle DataValidationError differently from a network or system error, while exception chaining keeps the original technical cause.

When should a bad record fail the whole batch?

It depends on the contract and risk. A required-schema failure or unexpectedly high reject rate may fail the batch. A small number of known malformed records may go to a quarantine table with reason codes, metrics, and an alert.

REST API ingestion, pagination, and retries

API ingestion is not just an HTTP request. A reliable design handles authentication, pagination, timeouts, rate limits, retries, checkpoints, schema validation, and idempotent writes.

Interview-ready answer

A REST API exposes resources through HTTP methods and status codes. A data ingestion client repeatedly requests pages, validates each response, persists data safely, and advances its checkpoint only after the page is committed.

Python - page iterator with bounded retry
import random
import time
import requests

RETRYABLE_STATUS = {429, 500, 502, 503, 504}

def get_json(session, url, params, max_attempts=4):
    for attempt in range(1, max_attempts + 1):
        try:
            response = session.get(url, params=params, timeout=(5, 30))
            if response.status_code not in RETRYABLE_STATUS:
                response.raise_for_status()
                return response.json()
        except (requests.Timeout, requests.ConnectionError):
            if attempt == max_attempts:
                raise
        else:
            if attempt == max_attempts:
                response.raise_for_status()

        delay = min(2 ** (attempt - 1), 30) + random.random()
        time.sleep(delay)

def iter_orders(base_url, token, updated_after=None):
    with requests.Session() as session:
        session.headers.update({"Authorization": f"Bearer {token}"})
        cursor = None

        while True:
            payload = get_json(
                session,
                f"{base_url}/orders",
                {"cursor": cursor, "updated_after": updated_after, "limit": 500},
            )
            yield from payload.get("items", [])
            cursor = payload.get("next_cursor")
            if not cursor:
                break

Pagination styles

StyleExampleRisk
Page number?page=3Concurrent inserts may shift pages
Offset/limit?offset=1000&limit=500Large offsets may be slow; shifting data can duplicate or skip

Safe checkpoint rule

Do not advance a cursor or watermark merely because the API request succeeded. Advance it after the corresponding records are validated and committed to durable storage. This prevents silent data loss after a downstream failure.

Retry rules
  • Always use a timeout. A request without one may hang indefinitely.
  • Use exponential backoff plus jitter so many clients do not retry together.
  • Set a maximum attempt count and emit a final failure metric.
  • Do not retry a non-idempotent write unless the API supports an idempotency key.
How would you make API ingestion idempotent?

Persist raw records with a stable business/event key, use upsert or deduplication at the target, checkpoint only committed pages, and make reruns read the same interval safely. For timestamp watermarks, include a small overlap and deduplicate by key plus latest update time.

Datetime and time zones

Time bugs cause missed increments, duplicate records, and wrong daily totals. The safest default is timezone-aware UTC internally, with conversion only at system boundaries.

Interview-ready answer

A naive datetime has no time-zone information; an aware datetime has a tzinfo and represents an unambiguous instant. Store and compare aware UTC timestamps, keep the source zone when it has business meaning, and format timestamps in an ISO 8601 form.

Python
from datetime import datetime, timezone
from zoneinfo import ZoneInfo

# Parse an ISO timestamp with an offset
source_time = datetime.fromisoformat("2026-07-22T09:30:00+05:30")
utc_time = source_time.astimezone(timezone.utc)

# Convert only for display or local business rules
india_time = utc_time.astimezone(ZoneInfo("Asia/Kolkata"))

print(utc_time.isoformat())    # 2026-07-22T04:00:00+00:00
print(india_time.isoformat())  # 2026-07-22T09:30:00+05:30

Event time vs processing time

TermMeaningExample
Event timeWhen the business event actually happenedCustomer clicked at 09:30
Ingestion timeWhen the platform received itEvent Hub received at 09:31
Processing timeWhen a job processed itSpark processed at 09:35
Common mistakes
  • Comparing an aware datetime with a naive datetime raises an error or encourages unsafe zone removal.
  • Attaching a zone with replace(tzinfo=...) does not convert clock time; it only labels it. Use astimezone for conversion.
  • Using only a timestamp watermark can miss multiple records with the same timestamp. Use a tie-breaker such as (updated_at, id).
  • Local midnight and daylight-saving changes can make a day shorter or longer than 24 hours in some zones.
Why store UTC if the business operates in one country?

UTC gives a stable comparison and ordering base, prevents ambiguity when systems or regions change, and simplifies cross-system integration. Keep the original offset or business zone when local-day reporting rules require it.

How do you handle a watermark when several rows share the same timestamp?

Use a composite checkpoint such as timestamp plus monotonically ordered ID, query with a deterministic condition, or re-read a small overlap and deduplicate. A plain greater-than timestamp filter can miss tied rows.

OOP for data engineering

You do not need a class for every pipeline step. OOP is useful when data and behavior belong together, multiple implementations share a contract, or dependencies must be replaced in tests.

Interview-ready answer

Object-oriented programming organizes state and behavior into objects. Encapsulation keeps an object's rules together, inheritance reuses or specializes behavior, and polymorphism lets different implementations satisfy the same interface.

Python
from abc import ABC, abstractmethod

class SourceReader(ABC):
    @abstractmethod
    def read(self):
        """Yield source records."""

class FileSourceReader(SourceReader):
    def __init__(self, path):
        self._path = path  # protected by convention

    def read(self):
        yield from read_json_lines(self._path)

class ApiSourceReader(SourceReader):
    def __init__(self, base_url, token):
        self._base_url = base_url
        self._token = token

    def read(self):
        yield from iter_orders(self._base_url, self._token)

def ingest(reader: SourceReader):
    for record in reader.read():  # polymorphism
        process(record)
PrincipleSimple meaningPipeline example
EncapsulationKeep state and its rules togetherAPI client owns session, auth, and retry policy
AbstractionExpose what callers need, hide detailsreader.read() hides file/API mechanics
InheritanceSpecialize a base contractFile and API readers implement a source interface
PolymorphismUse different implementations through one contractIngestion accepts any SourceReader
Prefer composition

A pipeline object should usually receive a reader, validator, and writer rather than inherit from all of them. Composition keeps responsibilities separate and makes unit testing easier.

Interview trap

Encapsulation in Python is mostly convention. A single leading underscore says an attribute is internal; double underscores trigger name mangling, not strict private access control.

Class vs function: how do you choose?

Use a function for a stateless transformation with clear inputs and outputs. Use a class when you need controlled state, resource lifecycle, multiple related operations, dependency injection, or interchangeable implementations.

What is method overriding?

A child class defines a method with the same name as the parent contract to provide specialized behavior. In the example, both readers override read, so callers can use either one polymorphically.

Unit testing and mocking

Test transformation logic directly, replace external boundaries with mocks or fakes, and keep integration tests for the real contracts between components.

Interview-ready answer

A unit test verifies one small unit of behavior in isolation. A mock replaces a dependency and records how it was used. An integration test verifies that multiple real components work together, such as parsing a sample file or writing to a test table.

Arrange, Act, Assert

Python - unittest
import unittest
from unittest.mock import Mock

def valid_orders(records, logger):
    result = []
    for row in records:
        if row.get("order_id") is None or row.get("amount", 0) < 0:
            logger.warning("Rejected order", extra={"order": row})
            continue
        result.append(row)
    return result

class TestValidOrders(unittest.TestCase):
    def test_rejects_negative_amount(self):
        # Arrange
        logger = Mock()
        rows = [{"order_id": 1, "amount": -5}]

        # Act
        result = valid_orders(rows, logger)

        # Assert
        self.assertEqual(result, [])
        logger.warning.assert_called_once()

    def test_keeps_valid_order(self):
        logger = Mock()
        row = {"order_id": 1, "amount": 5}
        self.assertEqual(valid_orders([row], logger), [row])
        logger.warning.assert_not_called()

if __name__ == "__main__":
    unittest.main()

Design for testability

Separate I/O from transformation. A function that accepts records and returns cleaned records is easier to test than one that reads a file, transforms rows, writes output, sends alerts, and changes a checkpoint in the same block.

Mocking trap

Patch the name where the code under test looks it up, not necessarily where the function was originally defined. Also avoid over-mocking: a test that only confirms your mock setup may prove nothing about real behavior.

Mock vs fake vs stub?

A stub returns predetermined data, a mock also verifies interactions, and a fake is a lightweight working implementation such as an in-memory repository. Terminology varies, so explain the behavior you need instead of relying only on the label.

What makes a good unit test?

Lazy evaluation, transformations, actions, and shuffle

Spark delays execution so it can optimize the complete plan. Performance depends heavily on whether transformations preserve partition locality or require a shuffle.

Interview-ready answer

A transformation returns a new DataFrame and adds work to the logical plan; an action asks Spark to produce a result and triggers execution. Lazy evaluation lets Spark combine and optimize transformations. A narrow transformation can compute each output partition from a small number of input partitions, while a wide transformation redistributes data across partitions and creates a shuffle boundary.

CategoryExamplesExecution effect
Transformationselect, filter, withColumn, join, groupByBuilds a new plan; remains lazy

NarrowFilter, map-like projection, union in common casesCan pipeline without all-to-all redistribution

Why shuffle is expensive

  1. Rows are serialized and written/read through shuffle storage.
  2. Data moves across the network between executors.
  3. Partitions may need sorting, hashing, and memory buffers.
  4. Skew can make one reducer task much larger than the rest.
  5. Spill to disk and garbage collection can increase runtime.

No. Several narrow transformations can be pipelined in one stage. A stage boundary normally appears when execution needs a shuffle dependency or another boundary such as certain input/output operations.

Spark sees the full expression before running it, so it can prune unused columns, push filters toward the source, combine expressions, choose physical operators, and avoid materializing intermediate results.

Interview-ready answer

Why can a window be expensive?

Rows with the same partition key must be brought together and usually sorted by the order columns, which can create shuffle and sort cost. Skewed keys can create very large partitions.

Use Spark SQL built-ins first. They are visible to Spark's optimizer, avoid row-by-row Python boundary cost, and usually handle nulls and code generation better.

Why is a Python UDF often slower?

Rows cross the JVM-Python boundary, values are serialized and deserialized, custom logic runs outside Spark's normal code generation path, and Spark cannot understand the function deeply enough to optimize it like a built-in expression.

Would you always replace a UDF?

No. Correctness and maintainability matter. If a required domain algorithm has no built-in equivalent, use a tested UDF, measure it, reduce its input columns/rows, and consider a vectorized implementation when appropriate.

Runtime partition vs storage partition

Spark/runtime partitionChunk processed by a taskControls execution parallelism

The concepts influence each other during reads and writes, but they are not the same. A table partition may contain many files, and each file may be split into one or more runtime partitions depending on source and settings.

How to choose a partition column

  • Frequently used in selective filters.
  • Moderate cardinality, not nearly unique per row.
  • Reasonably balanced data volume.
  • Stable business meaning and retention boundary.
  • Avoid columns that create thousands of tiny directories/files.
No magic partition count

There is no universal best number or file size. Start from data volume, available executor cores, operation type, skew, and target system. Measure task duration, input size, spill, scheduler overhead, and output file distribution. A commonly useful file-size range may be hundreds of MB, but the actual target is platform and workload dependent.

Why can coalesce(1) be dangerous?

It forces output through one partition and usually one task, which removes parallelism and may cause a long task or memory pressure. Use it only for genuinely small exports that require one file, not as a default formatting step.

Does repartition by a column guarantee one output file per value?

No. It controls hash distribution into Spark partitions, while partitionBy controls output directories. Multiple runtime partitions can write files into the same directory, and one task can write to multiple directories depending on data.

Spark performance: broadcast, skew, cache, and checkpoint

Tune from evidence: identify the slow stage, inspect the plan and task distribution, then address I/O, shuffle, skew, partition count, caching, or code shape.

A practical tuning order

  1. Confirm correctness, grain, and row counts.
  2. Read only needed partitions and columns; push filters early.
  3. Use efficient formats and built-in expressions.
  4. Inspect explain and the Spark UI for exchanges, join strategy, skew, spill, and repeated scans.
  5. Choose join strategy and partition count based on measured sizes.
  6. Persist only expensive reused results; unpersist after use.
  7. Address small files and output layout.

Broadcast join

Interview-ready answer

A broadcast join sends a small relation to executors so each executor can join its large-data partitions locally. This can avoid shuffling the large side, but the broadcast relation must be small enough for driver collection, network transfer, and executor memory.

PySpark

Broadcast risk

Do not broadcast based only on row count. Estimate serialized byte size and consider concurrent tasks. A relation with few rows but very wide values can still be large. Let Spark choose automatically when statistics are reliable; use a hint when you have evidence.

Data skew and salting

Interview-ready answer

Data skew means some partition keys contain far more data than others, so a few tasks run much longer than their peers. Salting splits a hot key into several artificial subkeys, performs the heavy operation in parallel, and then removes or recombines the salt.

PySpark - targeted salting sketch
from pyspark.sql import functions as F

salt_buckets = 8
hot_customer = "UNKNOWN"

salted_orders = orders.withColumn(
    "salt",
    F.when(
        F.col("customer_id") == hot_customer,
        (F.rand(seed=42) * salt_buckets).cast("int"),
    ).otherwise(F.lit(0)),
)

# Replicate only the hot dimension key across salts.
hot_dim = (
    customers.filter(F.col("customer_id") == hot_customer)
             .crossJoin(spark.range(salt_buckets).toDF("salt"))
)
normal_dim = (
    customers.filter(F.col("customer_id") != hot_customer)
             .withColumn("salt", F.lit(0))
)
salted_dim = normal_dim.unionByName(hot_dim)

result = salted_orders.join(salted_dim, ["customer_id", "salt"], "left").drop("salt")

Salting adds complexity and data expansion. First confirm skew in task metrics and consider adaptive skew handling, pre-aggregation, key correction, broadcast, or filtering.

Caching traps
  • Cache is lazy; it fills only when an action runs.

How do you detect skew?

In the Spark UI, compare task input size and duration within the same stage. A small number of tasks that process much more data or run much longer than the median are strong evidence. Also profile key frequencies and inspect the physical plan.

Cache is mainly for performance reuse and keeps lineage, so lost partitions can be recomputed. Checkpoint materializes data and truncates lineage, which is useful for very long plans or recovery boundaries but costs an additional write/read.

What would you do if a join is slow?

Validate cardinality; check filters and columns; inspect join strategy and statistics; measure side sizes; look for skew and spill; broadcast a genuinely small side; repartition or pre-aggregate when justified; and retest with stage metrics.

Structured Streaming uses the DataFrame API for unbounded data. Correct design requires an explicit schema, recovery checkpoint, event-time policy, output mode, and a sink that supports the required guarantees.

A watermark tracks event-time progress and lets Spark limit state for supported operations while defining how late data is handled.

Checkpoint vs watermark

ConceptPurposeDo not confuse with
CheckpointRecover source progress, query metadata, and state after restartA data-lateness policy
WatermarkTrack event-time progress and bound state/late handling for supported operationsA recovery directory or source offset

How the watermark moves

Conceptually, Spark observes the maximum event time seen and subtracts the configured delay. With a 20-minute delay and maximum seen event time of 10:00, the watermark is around 09:40. Data less late than the threshold is guaranteed not to be dropped by the watermark; data older than it may be dropped when the relevant state has been removed.

Output modes

ModeEmitsTypical fit
AppendOnly rows considered final for the queryImmutable events or finalized event-time windows
UpdateRows changed in the current triggerAggregates that evolve over time, with a compatible sink
CompleteEntire result table each triggerSmall aggregate result, not large detail data
Exactly-once answer

Spark can provide exactly-once processing for supported queries when the source is replayable, checkpointing is reliable, the transformation is deterministic, and the sink is idempotent or transactional. End-to-end exactly once is a property of the complete source-processing-sink design, not a phrase guaranteed by calling start().

Checkpoint rules
  • Every independent query needs its own checkpoint location.
  • Store checkpoints on reliable distributed storage, not temporary local disk.
  • Deleting a checkpoint usually starts a new query history and can reprocess data.
  • Some query changes are not compatible with an existing checkpoint; test deployment changes.
  • Keep business output and checkpoint paths separate.
Event time vs processing time window?

Event-time windows group by when events actually occurred and require a lateness policy. Processing-time windows group by when the engine processed events, so delayed events appear in later processing windows even if they happened earlier.

Why does a stateful aggregation need a watermark?

Without a lateness boundary, the engine may need to retain old group/window state indefinitely because another matching event could always arrive. A watermark allows eligible old state to be removed and controls memory/state growth.

Can you reuse one checkpoint for two output paths?

No. A checkpoint belongs to one logical streaming query and its progress. Sharing it across independent queries corrupts the recovery contract.

Streaming schema enforcement and error records

A production stream should preserve the raw payload, parse into an explicit schema, separate invalid records with reason codes, and monitor invalid rate without stopping for every bad event.

Interview-ready answer

Schema enforcement converts an incoming payload into a known typed contract. Parsing success is only the first layer; business validation then checks required fields, ranges, allowed values, uniqueness, and event-time validity. Invalid events go to a quarantine path with enough context to replay or repair them.

PySpark - valid/invalid stream split
from pyspark.sql import functions as F

    raw_events
    .withColumn("payload", F.from_json("value", event_schema))

         .when(F.col("payload.amount") < 0, "negative_amount"),

          .select(

Error record contract

  • Raw payload or a secure reference to it.
  • Machine-readable reason code and useful message.
  • Source system, partition/file, and offset/record identifier.
  • Ingestion and rejection timestamps.
  • Pipeline version and run/query identifier.
  • PII-safe logging and access controls.
Silent-null trap

from_json can return null when parsing fails. If you immediately select payload.* and filter null business keys, you may lose the raw reason. Create the parse-status/error column while the raw payload is still available.

Should one bad event stop the stream?

Usually a known record-level validation failure goes to quarantine while the stream continues and raises a quality metric. Fail the query for systemic problems such as incompatible contract changes, unavailable sinks, corrupted state, or an invalid rate above the agreed threshold.

How do you replay quarantined records safely?

Repair or map the records into the current contract, preserve their stable event IDs, write through an idempotent path, and track replay version/status. Do not simply append them if the target cannot deduplicate.

Delta output and idempotent writes

Your coding gate ends with partitioned Delta output. The important interview layer is how schema, partitioning, transactions, and reruns produce a reliable table.

Interview-ready answer

Delta Lake adds a transaction log and table-management features on top of data files. Spark readers use the log to identify a consistent table version, while transactional writes support reliable concurrent operations and patterns such as merge, schema enforcement, and time travel.

PySpark - partitioned Delta write

Write checklist

  • Target grain and business key are explicit.
  • Incoming rows are deduplicated deterministically.
  • Schema changes follow a controlled compatibility rule.
  • Partition column has useful filter patterns and reasonable cardinality.
  • Rerun strategy is tested with the same input twice.
  • Source, valid, invalid, inserted, and updated counts are reconciled.
Auto Loader bridge

In Azure Databricks, Auto Loader can incrementally discover new cloud files and track discovery/schema metadata. Its checkpoint and schema location solve different problems. The Azure/MAQ resource will cover Auto Loader, Delta operations, and governance in depth; here the required PySpark contract is explicit schema, deterministic transformation, and rerun-safe Delta output.

Merge trap

If multiple source rows match one target key, a merge can be ambiguous or fail. Deduplicate the source to one deterministic row per target key before merge. Also make the update condition explicit so an older event cannot overwrite a newer record.

Why is Parquet alone not the same as Delta?

Parquet is a columnar file format. Delta uses Parquet data files plus a transaction log that records table versions and actions, enabling consistent table semantics and operations such as transactional merge and time travel.

How would you prove a write is idempotent?

Run the same input twice and verify that target keys, row count, values, and reconciliation metrics remain correct. Also test partial failure between transformation, write, and checkpoint update.

def build_silver_orders(spark, bronze_path, customers):
    bronze = (
        spark.read
        .schema(event_schema)
        .json(bronze_path)
        .withColumn("source_file", F.input_file_name())
    )

    flattened = (
        bronze
        .select(
            "order_id",
            F.col("customer.id").alias("customer_id"),
            F.col("customer.country").alias("country"),
            "updated_at",
            "ingestion_id",
            "source_file",
            F.explode_outer("items").alias("item"),
        )
        .select(
            "order_id", "customer_id", "country", "updated_at",
            "ingestion_id", "source_file",
            F.col("item.line_id").alias("line_id"),
            F.col("item.sku").alias("sku"),
            F.col("item.quantity").alias("quantity"),
            F.col("item.price").alias("price"),
        )
        .withColumn("event_date", F.to_date("updated_at"))
        .withColumn("line_amount", F.col("quantity") * F.col("price"))
    )

    assessed = flattened.withColumn(
        "error_reason",
        F.when(F.col("order_id").isNull(), "missing_order_id")
         .when(F.col("line_id").isNull(), "missing_line_id")
         .when(F.col("customer_id").isNull(), "missing_customer_id")
         .when(F.col("updated_at").isNull(), "missing_updated_at")
         .when(F.col("quantity").isNull() | (F.col("quantity") <= 0), "invalid_quantity")
         .when(F.col("price").isNull() | (F.col("price") < 0), "invalid_price"),
    )

        assessed
        .filter(F.col("error_reason").isNotNull())
        .withColumn("rejected_at", F.current_timestamp())
    )

        Window.partitionBy("order_id", "line_id")
              .orderBy(F.col("updated_at").desc(), F.col("ingestion_id").desc())
    )

    latest = (
        valid
        .withColumn("row_num", F.row_number().over(latest_window))
        .filter(F.col("row_num") == 1)
        .drop("row_num")
    )

    customer_dim = customers.select(
        "customer_id",
        F.col("segment").alias("customer_segment"),
    )

    enriched = latest.join(
        F.broadcast(customer_dim),
        on="customer_id",
        how="left",
    )

        Window.partitionBy("customer_id")
              .orderBy("updated_at", "order_id", "line_id")
              .rowsBetween(Window.unboundedPreceding, Window.currentRow)
    )

    silver = enriched.withColumn(
        "customer_running_amount",
        F.sum("line_amount").over(running_window),
    )

    return silver, invalid

QuestionStrong short answer
List vs tuple?A list is mutable; a tuple is immutable and can be hashable when its elements are hashable. I use tuples for fixed records or composite keys.
Why set for membership?A set uses hashing, so average membership is O(1), compared with O(n) scanning in a list.
Shallow vs deep copy?A shallow copy creates a new outer container but shares nested objects; a deep copy recursively copies nested objects.
Why use a generator?It produces values lazily, so I can process large files or API results without storing the entire result in memory.
What does a context manager provide?It guarantees setup and cleanup around a block, such as closing a file even when an exception occurs.
Why avoid mutable default arguments?The default object is created once and reused across calls, causing state to leak between invocations.
How do you retry an API?I retry only transient failures with a timeout, bounded exponential backoff and jitter, respect rate-limit headers, and keep writes/checkpoints idempotent.
Naive vs aware datetime?A naive datetime has no zone information; an aware datetime represents an instant with a zone/offset. I normalize internal timestamps to aware UTC.
Unit vs integration test?A unit test isolates one behavior; an integration test verifies real component contracts such as parser-to-file or Spark-to-Delta.
Pandas vs PySpark?Pandas is ideal for data that fits one process and needs low overhead; PySpark is for distributed data and computation or an existing Spark platform.
Driver vs executor?The driver plans and coordinates the application; executors run tasks on partitions and hold cached/shuffle data.
Job, stage, task?An action creates a job, shuffle boundaries split it into stages, and each stage runs tasks across its partitions.
Transformation vs action?A transformation adds to a lazy plan and returns a DataFrame; an action requests a result and triggers execution.
Narrow vs wide transformation?A narrow transformation keeps dependencies local to a small number of parent partitions; a wide transformation redistributes rows and normally shuffles.
Why is shuffle expensive?It serializes, sorts/hashes, writes, transfers, and reads data across executors, and skew can leave a few very slow tasks.
Why explicit schema?It gives a stable contract, avoids inference cost and inconsistency, and makes type failures visible early.
groupByKey vs reduceByKey?For RDDs, groupByKey moves all values then groups them; reduceByKey combines values locally before shuffle and usually transfers less data. For structured data I prefer DataFrame aggregations.
Window vs groupBy?groupBy collapses groups; a window keeps row-level detail and adds rankings, running metrics, or previous/next values.
dropDuplicates vs row_number?dropDuplicates does not express which duplicate wins; row_number with deterministic ordering selects the required latest or highest-priority row.
Left semi vs left anti?Left semi returns left rows with a match; left anti returns left rows without a match. Neither returns right-side columns.
When broadcast join?When one side is safely small enough to distribute to executors, avoiding a shuffle of the large side. I verify byte size and the physical plan.
What is data skew?A few keys create much larger partitions, so a few tasks dominate stage time. I verify task metrics before applying targeted fixes such as salting.
repartition vs coalesce?repartition reshuffles to rebalance and can increase or decrease partitions; coalesce mainly reduces partitions with less movement and can be uneven.
cache vs checkpoint?Cache reuses computed data but keeps lineage; checkpoint materializes data and truncates lineage for recovery or very long plans.
Why prefer built-ins over Python UDF?Built-ins stay visible to Spark optimization and avoid much of the JVM-Python serialization cost.
What is a streaming checkpoint?Reliable metadata that stores query progress and state so a streaming query can recover after restart.
What is a watermark?An event-time progress boundary used by supported stateful operations to handle lateness and remove old state.
Can late data still be processed?Yes, if it arrives before the relevant state is finalized/removed. Data older than the watermark may be dropped depending on the operation.
What gives exactly-once?A replayable source, reliable checkpoint, deterministic processing, and an idempotent or transactional sink together provide the end-to-end guarantee.
Why can append duplicate Delta rows?Append adds new files/rows and does not know they represent the same business keys; rerun safety requires dedup, overwrite scope, or merge.
