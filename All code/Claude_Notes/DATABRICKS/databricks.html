1. What is Azure Databricks

Azure Databricks is a cloud-based, unified data analytics platform built on Apache Spark, offered as a first-party Azure service. In one line: it's where data engineers, data scientists, and analysts process huge amounts of data, build ETL pipelines, and train ML models — all on managed Spark clusters, collaboratively, in notebooks.

If raw data is a mountain of ore, Spark is the giant processing machine that crushes it in parallel. Databricks is the fully-staffed, managed factory built around that machine — it spins up the machine on demand (clusters), gives everyone shared workbenches (notebooks), keeps the products reliable (Delta Lake), and handles security and the electricity bill for you.

Why companies use it (say this)

  • Managed Spark — spin up auto-scaling clusters in minutes; no infrastructure headache.
  • Unified platform — data engineering, analytics, and ML in one place (one team, one tool).
  • Collaborative notebooks — Python, SQL, Scala, R in the same workspace.
  • Deep Azure integration — ADLS, Azure Data Factory, Synapse, Azure AD, Key Vault.
  • Delta Lake + Lakehouse — reliability (ACID) of a warehouse on cheap lake storage.
PaaS, and a key fact: Azure Databricks is a PaaS offering. It's not "just Spark hosted on Azure" — Microsoft + Databricks added Azure AD authentication, optimized runtime, and tight Azure integration. ADF usually orchestrates, and Databricks does the heavy transformation.

2. Apache Spark & Databricks vs Spark

Apache Spark is the open-source, in-memory, distributed processing engine at the core. It splits big jobs into small tasks and runs them in parallel across many machines (a cluster), keeping data in memory for speed.

Databricks vs open-source Spark (common question)

Open-source SparkDatabricks
You install & manage it yourselfFully managed clusters, spin up in minutes
Just the engineEngine + collaborative notebooks, jobs, governance, security
Standard performanceDatabricks Runtime with optimizations + Photon (C++ vectorized engine)
No built-in reliability layerDelta Lake for ACID transactions

Spark's languages: Python (PySpark), Scala, SQL, R, Java. For data engineering, PySpark and SQL dominate.

5. Clusters (All-Purpose vs Job)

A cluster is a set of compute machines (a driver + workers) that run your Spark code. Knowing the two types and when to use each is a guaranteed question.

All-Purpose ClusterJob Cluster
PurposeInteractive development, exploring, collaborative notebooksRunning a scheduled/automated job
LifecycleStays on; multiple users share itCreated when the job starts, terminated when it ends
CostCostlier (idle time burns money)Cheaper for production (no idle cost)
Use forDev & testingProduction pipelines
Interview Tip — cost answer: "For production I use Job Clusters — they spin up for the run and shut down after, so we don't pay for idle compute. All-Purpose clusters are for interactive dev only." This signals cost awareness.

Key cluster pieces: a driver node (coordinates, runs the main program, builds the DAG) and worker/executor nodes (do the actual parallel work). Autoscaling adds/removes workers based on load; auto-termination shuts an idle cluster down to save cost.

6. Workspace, Notebooks & Jobs

  • Workspace: the environment where you organize notebooks, libraries, dashboards, and folders.
  • Notebooks: interactive documents with code cells. You can mix languages with magic commands (%python, %sql, %scala, %md). Great for collaboration.
  • Jobs: a way to schedule and automate notebooks or scripts to run on a cluster (the production way to run pipelines). Supports retries, alerts, and dependencies (Databricks Workflows).
  • DBFS (Databricks File System): an abstraction layer over cloud storage for storing/managing files.
  • Secrets & Scopes: store sensitive values (keys, tokens) securely. Limit: 1000 secrets per scope, 128 KB max each.

7. Databricks Runtime (DBR) & Photon

The Databricks Runtime (DBR) is the set of core software that runs on clusters. It includes Apache Spark plus Databricks' optimizations: Delta Lake, optimized connectors, and performance features. You pick a DBR version when creating a cluster.

Photon is Databricks' next-gen vectorized query engine written in C++. It dramatically speeds up SQL and DataFrame workloads by using modern CPU efficiency, without changing your code. Mentioning Photon shows you're current.

9. Transformations vs Actions ⭐

This is a fundamental, near-guaranteed Spark question.

🔧 Transformations (lazy)

Define a new DataFrame from an existing one, but don't run immediately — Spark just builds a plan.

Examples: select(), filter(), withColumn(), groupBy(), join(), map().

⚡ Actions (trigger execution)

Actually run the whole built-up plan and return a result or write output.

Examples: show(), count(), collect(), write(), take().

Interview Tip: "Transformations are lazy — Spark records them as a plan (DAG) but waits. Nothing executes until an action is called. This laziness lets Spark optimize the whole chain together (e.g., push filters earlier)." Always mention laziness — it's the point of the question.
Watch out: collect() pulls all data to the driver — on a big dataset it causes Out-Of-Memory. Use show() or take(n) to peek instead.

10. Narrow vs Wide Transformations & Shuffle ⭐

Narrow TransformationWide Transformation
Data movementEach output partition needs data from one input partition — no shuffleOutput partition needs data from many partitions — shuffle across the network
SpeedFast & cheapSlow & expensive (network + disk I/O)
Examplesmap(), filter(), select()groupBy(), join(), distinct(), reduceByKey()

A shuffle is when Spark redistributes data across partitions/nodes — it's the biggest performance killer. Wide transformations cause shuffles. The whole game of optimization is minimizing shuffles.

Interview gold: "I minimize wide transformations — for example, filter before join so less data shuffles, and use broadcast joins when one table is small. reduceByKey is better than groupByKey because it pre-aggregates locally before the shuffle, sending far less data."

11. Lazy Evaluation, DAG & Stages

  • Lazy Evaluation: transformations aren't run until an action is called; Spark builds a logical plan first, then optimizes the whole thing.
  • DAG (Directed Acyclic Graph): the plan of all transformations. "Directed" (ordered steps), "Acyclic" (no loops). Spark uses it to plan execution and to recompute lost data (lineage).
  • Stages & Tasks: the DAG is split into stages at every shuffle (wide transformation) boundary. Each stage = a set of tasks, one task per partition, running in parallel.
  • Catalyst Optimizer: Spark SQL's engine that rewrites your query for speed (predicate pushdown, column pruning, etc.) automatically.
Pro debugging tip to mention: "When a job is slow, I read the Spark UI → Stages tab to find the slow stage and see how many shuffles/tasks it created — that tells me exactly what to tune." Interviewers love hearing you use the Spark UI.

12. Partitioning: repartition vs coalesce

Partitioning splits data into chunks processed in parallel across the cluster. Good partitioning = good parallelism. Two methods to change partition count:

repartition(n)coalesce(n)
DoesIncrease OR decrease partitionsOnly decrease partitions
Shuffle?Full shuffle (expensive)Avoids full shuffle (merges existing partitions) — cheaper
Use whenIncreasing parallelism or evenly redistributing before a wide opReducing partitions, e.g. before writing output
Interview Tip: "To reduce partitions I prefer coalesce (no full shuffle). I use repartition when I need to increase parallelism or evenly spread skewed data. Rule of thumb: 2–4 partitions per CPU core, each ~100s of MB." This rule-of-thumb impresses interviewers.
Small File Problem: writing thousands of tiny files makes future reads slow. Fix: coalesce(n) or repartition(n) before writing to produce fewer, bigger files.

13. Cache vs Persist

Both store a DataFrame in memory so it isn't recomputed every time it's reused (Spark recomputes from scratch by default due to laziness).

  • cache() = shorthand for persist(MEMORY_AND_DISK) — one default storage level.
  • persist(level) = lets you choose the storage level (MEMORY_ONLY, MEMORY_AND_DISK, DISK_ONLY, etc.).

When to use: when the same DataFrame is used multiple times (e.g., joined twice, or used in a loop). Caching it once avoids re-reading/recomputing. Remember to unpersist() when done to free memory.

14. Broadcast Join & Data Skew ⭐

Broadcast Join

A broadcast join sends a small table to every worker node's memory, so a big table can be joined without shuffling it across the network. Huge speedup when one side is small.

# force a broadcast join (small_df under ~100 MB)
from pyspark.sql.functions import broadcast
result = big_df.join(broadcast(small_df), "id")

Spark auto-broadcasts tables under spark.sql.autoBroadcastJoinThreshold (default 10 MB). For bigger-but-still-small tables, hint it explicitly with broadcast().

Data Skew (advanced but valued)

Data skew = a few partitions hold way more data than others, so most tasks finish fast but one or two "straggler" tasks take forever. Signs: in the Spark UI one task runs much longer than the rest.

Fixes: salting (add a random prefix to the join key to spread hot keys across partitions), use a broadcast join if one side is small, increase parallelism, or enable Adaptive Query Execution (AQE) which auto-handles skew.

15. Performance Optimization (Top Levers)

When asked "your Spark job is slow, how do you optimize?", give a structured list:

  1. Enable AQE (Adaptive Query Execution) — auto-coalesces small partitions & fixes skew at runtime.
  2. Broadcast small tables in joins to avoid shuffle.
  3. Cache reused DataFrames.
  4. Partition large datasets by the most-filtered column; right-size partitions.
  5. Filter early (predicate pushdown) — reduce data before joins/aggregations (prefer narrow over wide).
  6. Use DataFrames, not RDDs (Catalyst + Tungsten optimizations).
  7. Use built-in functions, not Python UDFs — UDFs are slower (no Catalyst optimization).
  8. Use Parquet/Delta (columnar, compressed) over CSV/JSON.
  9. Right-size the cluster — often more memory per worker beats more workers.
Interview Tip: Start the answer with "First I'd open the Spark UI Stages tab to find the slow stage — then tune." Diagnosing before tuning shows real experience. Also: "avoid groupByKey, prefer reduceByKey" and "avoid UDFs when a built-in exists" are classic winning points.

16. Delta Lake (ACID) ⭐ Must-Know

Delta Lake is an open-source storage layer that brings reliability to data lakes. It sits on top of Parquet files in your storage (ADLS) and adds the warehouse-grade features a plain data lake lacks. This is the heart of every Databricks data engineering interview.

What Delta Lake gives you

  • ACID transactions: reads/writes are reliable and consistent even with concurrent users — no half-written, corrupt data.
  • Schema enforcement: rejects writes with the wrong schema (no garbage data sneaking in).
  • Schema evolution: intentionally allow new columns with the mergeSchema option.
  • Time Travel: query older versions of the table (audit, rollback, reproduce).
  • Upserts & deletes: via MERGE — impossible in plain Parquet.
  • Unified batch + streaming: the same Delta table can be a streaming source and sink.

How it works under the hood (good to mention): a Delta table = Parquet data files + a transaction log (the _delta_log folder, JSON). The log records every change in order — that's what enables ACID, time travel, and concurrency.

Interview Q
"What is Delta Lake and why use it over plain Parquet?"
Why they ask: the single most important Databricks data-engineering concept.
"Plain Parquet on a lake has no transactions, no updates/deletes, and no schema guarantees. Delta Lake adds a transaction log on top of Parquet to give ACID transactions, schema enforcement/evolution, time travel, and MERGE-based upserts — turning a data lake into a reliable Lakehouse."

17. OPTIMIZE, Z-ORDER, VACUUM & Time Travel

These Delta maintenance commands come up constantly — know what each does and the gotchas.

CommandWhat it does
OPTIMIZECompacts many small files into fewer large ones (fixes the small-file problem, speeds reads).
ZORDER BY (col)Used with OPTIMIZE — co-locates related data in the same files so Spark can skip files (data skipping). Use on high-cardinality columns you filter on often (e.g., customer_id).
VACUUMPermanently deletes old data files no longer referenced, older than a retention threshold (default 7 days) to save storage cost.
Time TravelQuery a past version: SELECT * FROM t VERSION AS OF 5 or TIMESTAMP AS OF '2026-01-01'.
The classic VACUUM trap: once you VACUUM away old files, you can no longer Time Travel back to versions that depended on them. So VACUUM saves cost but destroys old history — interviewers love this gotcha.

18. MERGE / Upsert & Incremental Processing

MERGE (upsert) is how you apply changes — insert new rows, update changed ones, optionally delete — in a single atomic operation. It's the backbone of incremental loads and SCD/CDC in Databricks.

MERGE INTO target t
USING updates u ON t.id = u.id
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *

Incremental processing

Instead of reprocessing all data nightly, process only new/changed data:

  • Use a watermark column (e.g., last_modified) to read only newer rows.
  • Apply changes with MERGE (Delta's CDC pattern) — handles inserts + updates in one go.
  • For streaming ingestion, use Auto Loader (next section) which tracks what's already processed.
Interview Tip: "I implement incremental loads with a watermark to pull only changed records, then a Delta MERGE to upsert them into the target — far cheaper than full reloads, and MERGE keeps it atomic." This is a gold-standard answer.

19. Medallion Architecture ⭐ Must-Know

The Medallion architecture (Bronze → Silver → Gold) is the standard way to organize a Lakehouse pipeline into quality layers. Expect to draw or explain this in almost every interview.

🥉 BRONZE
Raw ingested data, stored as-is with minimal change. Add metadata like _ingest_time, _source_file. Streamed in via Auto Loader / Kafka.
→
🥈 SILVER
Cleaned & conformed: handle nulls, deduplicate, join, standardize, apply CDC with MERGE. Partition by business date. "Single source of truth."
→
🥇 GOLD
Business-ready aggregates: KPIs, summary tables for BI/dashboards/ML. Optimized with OPTIMIZE + ZORDER. Consumed by analysts.

Interview Q
"How would you structure Bronze, Silver, and Gold layers for an enterprise platform?"
Why they ask: tests whether you can design a real, layered Lakehouse pipeline.
"Bronze stores raw data as-is with ingestion metadata (via Auto Loader). Silver cleans, deduplicates, and conforms it — applying CDC with Delta MERGE and partitioning by business date. Gold holds aggregated, business-ready tables optimized with OPTIMIZE + ZORDER for BI. I orchestrate the three stages with Databricks Workflows and add alerts."

20. Auto Loader & Structured Streaming

Auto Loader is Databricks' efficient way to incrementally ingest new files as they land in cloud storage (ADLS/S3) — without reprocessing old files. It tracks which files it has already seen, so each run picks up only new data.

# Auto Loader reads only new files as they arrive
df = (spark.readStream
        .format("cloudFiles")
        .option("cloudFiles.format", "json")
        .option("cloudFiles.schemaLocation", "/mnt/schema")
        .load("/mnt/raw/"))

Structured Streaming is Spark's engine for processing live/continuous data as a stream (micro-batches). The same Delta table works as both a streaming source and sink. Use checkpointing for fault tolerance (it remembers progress) and aim for idempotent writes so reruns don't duplicate data.

Scenario answer: "5 GB of JSON daily, slow to process?" → "Ingest with Auto Loader (only new files), store as Delta/Parquet (not raw JSON), avoid wide schemas at ingestion, and partition sensibly. Then transform downstream." This is a very common scenario question.

21. Delta Live Tables (DLT)

Delta Live Tables (DLT) is a framework for building reliable, declarative data pipelines. Instead of writing all the orchestration code, you declare the transformations and DLT manages dependencies, error handling, retries, and data-quality checks.

  • Declarative: you define the "what" (tables + transformations); DLT handles the "how" (execution order, infra).
  • Expectations: built-in data-quality rules (e.g., drop or fail rows that don't meet a condition).
  • Great fit for building the Bronze→Silver→Gold flow with less boilerplate.

22. Unity Catalog & Governance

Unity Catalog is Databricks' unified governance layer for data and AI — increasingly asked in 2025/26 interviews. It centralizes access control, auditing, and discovery across all workspaces.

  • Centralized access control: manage permissions on tables/views/files in one place with a standard SQL grant model.
  • Three-level namespace: catalog.schema.table — organizes data cleanly.
  • Data lineage: automatically tracks how data flows table-to-table (great for audits).
  • Auditing & discovery: see who accessed what; search data assets.
One-liner: "Unity Catalog gives one consistent governance and permission model across all Databricks workspaces, with a three-level namespace, built-in lineage, and auditing."

23. Security & Secrets

  • Azure AD (Entra ID): identity & authentication; integrates with Databricks for SSO and access.
  • Secret Scopes: store credentials/keys securely; reference them in code instead of hardcoding. Can be backed by Azure Key Vault.
  • Managed Identity / Service Principal: password-less, secure access to ADLS and Azure services.
  • RBAC + Unity Catalog: control who can read/write which data.
  • Encryption: data encrypted in transit and at rest; data stays in your own storage (data plane).
Interview Tip: Say "I never hardcode credentials — I use secret scopes backed by Azure Key Vault and authenticate with a Managed Identity / Service Principal." That's the secure-design phrasing they want.

24. CI/CD & Orchestration

  • Git integration (Repos): connect notebooks to Azure DevOps / GitHub for version control and feature branches.
  • CI/CD: automate tests and deploy with Azure DevOps / GitHub Actions; deploy jobs & clusters via the Databricks CLI / REST API or Databricks Asset Bundles.
  • Orchestration: use Databricks Workflows/Jobs to schedule multi-task pipelines, or trigger Databricks notebooks from Azure Data Factory (ADF orchestrates, Databricks transforms).
Common real-world flow: ADF (or Workflows) triggers a Databricks notebook → notebook reads from ADLS Bronze → transforms through Silver → writes Gold Delta tables → Power BI / Synapse reads Gold for reporting.

25. Real Scenario-Based Questions

Scenario
"A pipeline failed overnight while writing to a Delta table. How do you debug & recover?"
Approach: "Check the job run + Spark UI for the failed stage and error. Because Delta is ACID, a failed write won't half-commit — the table stays consistent. I can Time Travel to the last good version to verify, rerun the job (idempotent writes + checkpointing prevent duplicates), and add retries/alerts so it self-heals next time."
Scenario
"You receive raw 5 GB JSON files daily; Databricks processing is painfully slow. What do you do?"
Approach: "Ingest with Auto Loader (only new files, not full reload), convert/store as Delta/Parquet (columnar, compressed) instead of JSON, avoid wide schemas at ingest, partition by date, and run OPTIMIZE to fix small files. Push filters early to cut data before joins."
Scenario
"Business wants hourly aggregated KPIs without reprocessing all data each time."
Approach: "Use incremental processing — Structured Streaming or scheduled incremental batches reading only new Silver data via watermark, then MERGE/aggregate into Gold hourly. Materialize KPIs in a Gold Delta table optimized with ZORDER."
Scenario
"Your join is extremely slow on a huge table. How do you fix it?"
Approach: "Check if one side is small → use a broadcast join to skip the shuffle. If both are big, ensure they're partitioned on the join key, filter before joining, and check for data skew (one giant key) — fix with salting or AQE. Read the Spark UI to confirm where the shuffle is."
Scenario
"How do you integrate Databricks with other Azure services in a project?"
Approach: "Storage in ADLS Gen2, orchestration via Azure Data Factory (triggers Databricks notebooks), secrets in Key Vault, identity via Azure AD, and serve curated Gold tables to Synapse / Power BI. Databricks does the heavy Spark transformation in the middle."
