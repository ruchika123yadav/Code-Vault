1. What is Azure Data Factory & Why Companies Use It

Azure Data Factory (ADF) is a cloud-based, serverless data integration and orchestration service. In plain words: it's a tool that moves data from many sources to a destination, transforms it on the way, and schedules + monitors the whole workflow — without you managing any servers.

Think of ADF as a factory assembly line for data. Raw materials (data) come in from many suppliers (databases, files, APIs). The assembly line (pipeline) moves them station to station, cleans and reshapes them (transformation), and ships the finished product (clean data) to a warehouse (Azure SQL, Synapse, Data Lake) where business teams use it for reports and dashboards.

Why companies use it (say this in the interview)

  • It supports both on-premises and cloud sources (90+ built-in connectors).
  • It separates orchestration from processing — ADF coordinates the work, while heavy compute can be pushed to Databricks/Synapse.
  • It scales automatically and is serverless (you pay per use, no infrastructure to manage).
  • It integrates tightly with the Azure ecosystem (Data Lake, Synapse, Key Vault, Monitor, DevOps).
Interview Tip: A weak candidate says "ADF is an ETL tool." A strong candidate says "ADF is a serverless orchestration service that ingests data from many sources, coordinates movement and transformation, and schedules/monitors the workflow — companies use it because it handles hybrid sources and scales without infrastructure management." Always add the why.
Interview Q
"What is Azure Data Factory and why do companies use it?"
Why they ask: to check if you understand ADF's purpose, not just a definition.
Answer with the serverless orchestration definition + the 4 "why" points above + one real example like "we used it to ingest daily sales files from on-prem SQL Server into Azure Data Lake."

2. ETL vs ELT & Where ADF Fits

ETL = Extract, Transform, Load. ELT = Extract, Load, Transform. The difference is when you transform the data.

AspectETLELT
OrderTransform before loading into targetLoad raw first, transform inside the target
Transform happens inA separate engine (e.g., Data Flow / Databricks)The powerful target system (Synapse, SQL, Spark)
Best whenTarget is less powerful, or you need clean data on arrivalTarget is a powerful warehouse / lake that can crunch raw data

ADF supports both patterns. It can transform in flight (Mapping Data Flows) for ETL, or just load raw data and call Databricks/Synapse to transform for ELT. Modern cloud projects often lean ELT because cloud warehouses are cheap and powerful.

Interview Q
"What's the difference between ETL and ELT, and which does ADF use?"
Why they ask: to test if you understand modern cloud data patterns.
Explain the order difference, then say "ADF supports both; in cloud projects we often prefer ELT because the warehouse (Synapse/Databricks) can transform raw data at scale cheaply."

4. Pipelines & Activities

A pipeline is a workflow definition, not a data container. It defines execution order, controls dependencies, manages retries/failures, and coordinates multiple activities. In production, a pipeline usually represents a business process — like "daily sales ingestion" or "end-of-day reporting prep."

The three families of activities

TypePurposeExamples
Data MovementMove data from source to destinationCopy Activity
Data TransformationReshape / clean / aggregate dataMapping Data Flow, Databricks Notebook, Stored Procedure, HDInsight, Azure Function
Control FlowDirect the logic and flow of the pipelineForEach, If Condition, Switch, Until, Wait, Lookup, Get Metadata, Execute Pipeline, Set Variable

Three ways to run a pipeline

  • Debug: test/troubleshoot while developing, before publishing.
  • Trigger Now: manual one-off run on demand.
  • Trigger (scheduled/event): automated runs on a schedule or when an event happens.
Interview Q
"What is a pipeline? Is it where the data is stored?"
Why they ask: a subtle trap — to see if you think a pipeline holds data.
Clarify firmly: "No — a pipeline does not store data. It's a workflow definition that orchestrates activities in order, handles dependencies and retries. The data lives in the source/sink stores, not in the pipeline."

5. Linked Services vs Datasets

This pair gets confused constantly, so interviewers test it. Keep it crisp:

🔌 Linked Service = "WHERE"

The connection information to an external resource — server name, authentication, credentials. Like a connection string.

Two uses: connect to a data store (SQL, Blob), or connect to a compute (Databricks, HDInsight).

📦 Dataset = "WHAT"

A named view of the data you want to use — which table, which folder, which file format. It always points to a Linked Service.

Example: a Dataset "Customers" = the dbo.Customers table, using the SQL Linked Service.

Linked Service = your friend's home address + house key. Dataset = the specific room and cupboard inside that house you want to open. You need the address first (Linked Service), then you point to the cupboard (Dataset).

6. Integration Runtime (IR) — Very Important

The Integration Runtime (IR) is the compute infrastructure ADF uses to actually perform data movement, dispatch activities, and run transformations. It's the bridge between ADF's instructions and the real work. There are three types — knowing when to use each is a guaranteed question.

IR TypeUse it forKey point
Azure IR (default)Cloud-to-cloud data movement & transformationFully managed & serverless by Microsoft; auto-scales
Self-Hosted IR (SHIR)On-premises or private-network (VNet) sourcesYou install it on a local machine/VM; bridges on-prem ↔ cloud through firewalls
Azure-SSIS IRRunning existing SQL Server Integration Services (SSIS) packages in the cloudLets you lift-and-shift legacy SSIS workloads to Azure
Interview Tip — the classic scenario: "You need to copy data from an on-premises SQL Server to Azure Blob Storage. Which IR?" → Self-Hosted IR, because the on-prem server sits behind a firewall and Azure IR can't reach it directly. Explain the why (security/connectivity), not just the name.
Interview Q
"When do you use a Self-Hosted Integration Runtime?"
Why they ask: to test hybrid architecture understanding.
"When accessing on-prem systems, connecting to private/VNet networks, or when firewall/security rules block direct cloud access. The SHIR runs inside the private network and securely pushes data to the cloud."

7. Copy Activity (Data Movement)

The Copy Activity is the most used activity in ADF. It moves data from a source to a sink (destination). Used for ETL and "lift-and-shift" data movement.

What it handles in real projects

  • Bulk ingestion & incremental loads
  • Schema mapping (mapping source columns to sink columns)
  • Data type conversions
  • Format conversions (e.g., CSV → Parquet)

Every Copy Activity has a Source (where data comes from) and a Sink (where it goes). For performance you tune parallelism, batch size, and Data Integration Units (DIUs) — more on this in Section 18.

Staging tip: For large loads into Synapse, enable staged copy (data lands in Blob/ADLS first, then PolyBase/COPY loads it into the warehouse). This is much faster than a direct row-by-row insert.

8. Mapping Data Flows & Wrangling Data Flows

Mapping Data Flows let you build visual, code-free data transformations. You design the logic (joins, filters, aggregations) on a canvas, and ADF runs it on scaled-out Apache Spark clusters that it fully manages — you don't write or manage any Spark code.

Common transformations

Join, Lookup, Conditional Split, Aggregate, Derived Column, Filter, Sort, Union, Pivot/Unpivot, Surrogate Key, Alter Row (for upserts/deletes).

Join types supported

Inner, Left Outer, Right Outer, Full Outer, Cross, plus Semi (rows in left that match right) and Anti (rows in left with no match).

Mapping vs Wrangling Data Flow

Mapping Data FlowWrangling Data Flow
PurposeComplex, large-scale ETL transformationsLight, interactive data prep / exploration
Engine / languageVisual designer on managed SparkPower Query (M language)
Best forJoins, aggregations, cleansing at scaleQuick filtering, reshaping, ad-hoc wrangling
Interview Tip: Data Flows run on Spark clusters that take a few minutes to "warm up" (cluster startup time). Mention this — it's why Data Flows aren't ideal for tiny, frequent jobs; for simple moves, a Copy Activity is cheaper and faster.

Interview Q
"When would you use a Data Flow instead of a Copy Activity?"
Why they ask: to see if you know transformation vs movement.
"Copy Activity is for moving data with minimal change. I use a Mapping Data Flow when I need real transformations — joins across sources, aggregations, conditional splits, cleansing — without writing Spark code. For heavy custom logic I'd instead call Databricks."

10. Triggers & Scheduling

A trigger decides when a pipeline runs. There are three types — and the differences are a favorite question.

TriggerHow it firesBest use case
Schedule TriggerAt fixed clock times (e.g., daily 2 AM, every hour)Regular batch jobs on a calendar
Tumbling Window TriggerFixed-size, non-overlapping time windows, with stateTime-series / incremental batches needing retry & backfill
Event-Based TriggerWhen an event happens (e.g., a file lands in Blob via Event Grid)Near real-time, file-arrival ingestion

Schedule vs Tumbling Window (common follow-up)

  • Schedule is "fire and forget" at clock times; it doesn't track windows or dependencies.
  • Tumbling Window processes discrete, non-overlapping time slices, remembers state, supports retry and backfill (re-running old windows), and supports dependencies between windows. Great for SLA-driven, time-series pipelines.
Key facts interviewers test: A pipeline can have multiple triggers, and one trigger can fire multiple pipelines (many-to-many). Triggers can pass parameters, and can be paused/resumed. Event triggers work with Blob + Event Grid events (file created/deleted).

11. Parameters vs Variables

ParametersVariables
Set when?Before the run starts (passed in)During the run
Changeable at runtime?No — read-only during the runYes — via Set Variable / Append Variable activities
Main purposeReusability (e.g., environment name, file path)Dynamic logic within a run (counters, flags, building values)

Quick memory hook: Parameters make a pipeline reusable; Variables make it dynamic. You consume a parameter with @pipeline().parameters.X and a variable with @variables('X').

System variables are built-in read-only values ADF provides automatically, like @pipeline().RunId, trigger time, pipeline name — useful for logging and audit columns.

12. Dynamic / Metadata-Driven Pipelines

This is a maturity question — it shows you can design for scale instead of hardcoding. A metadata-driven pipeline reads its configuration from a control table or file, then loops over it, instead of building one pipeline per table.

How it works (say this)

  1. A Lookup activity reads a control/metadata table (a list of source tables, paths, settings).
  2. A ForEach activity loops over that list.
  3. Inside the loop, a parameterized Copy/Data Flow uses dynamic content (@item().tableName) to process each item.

Result: one pipeline handles 100 tables instead of 100 separate pipelines. Less duplication, easy maintenance.

Star line in interviews: "Instead of hardcoding, I build metadata-driven pipelines — a control table lists all sources, a Lookup reads it, a ForEach loops, and parameterized datasets/linked services process each entry dynamically. To onboard a new table, I just add a row to the control table — no new pipeline needed."

13. Control Flow Activities

Control flow activities direct the logic of a pipeline (not data movement). Know what each does:

ActivityWhat it does
ForEachLoops over a collection (array/list) — sequentially or in parallel
If ConditionBranches based on a true/false expression
SwitchBranches into multiple paths based on a value (like a switch-case)
UntilLoops until a condition becomes true
WaitPauses the pipeline for a set time
LookupReads a single value or a row set (e.g., from a config table)
Get MetadataReturns properties of a file/folder (name, size, exists, child items)
Execute PipelineCalls another pipeline (modular, reusable design)
Set / Append VariableAssigns or builds variable values during the run

Lookup vs Get Metadata (frequently confused)

LookupGet Metadata
ReturnsData rows / values from a datasetProperties about a file/folder (name, size, exists)
Typical useRead a watermark value or config rowsCheck if a file exists / list files before looping
⚠️ LimitMax 5,000 rows / 2 MB JSON outputMax 8,000 child items
Interviewers love the Lookup limit: if you Lookup a huge table you'll hit the 5,000 row / 2 MB cap. For large config, filter at source or read it differently. Knowing this caveat instantly marks you as someone with real experience.

14. Incremental Load (Watermark) ⭐ Must-Know

This is THE most-asked scenario for 1–2 year roles. Incremental loading means loading only new or changed records since the last run — instead of reloading the entire table every time. It saves time, compute, and money.

1 Lookup reads last watermark
(e.g., last LoadDate from a control table)
↓
2 Lookup gets current max value from source
(e.g., MAX(LastModifiedDate) in source table)
↓
3 Copy Activity pulls only rows between
old watermark < rows ≤ new watermark
↓
4 On success, update the watermark
(store the new max in the control table via Stored Procedure)

How to explain it (step by step)

  1. Keep a watermark column in the source — usually a LastModifiedDate timestamp or an ever-increasing ID.
  2. Store the last processed watermark value in a small control table (or pipeline variable).
  3. Each run: a Lookup reads the old watermark; another reads the current max from source.
  4. The Copy Activity uses a query like WHERE LastModifiedDate > @oldWatermark to fetch only new/changed rows.
  5. After a successful load, update the watermark (via a Stored Procedure activity) so the next run starts from there.

Other ways to do incremental load

  • Change Data Capture (CDC) / Change Tracking: if the source database supports it, it tells you exactly which rows changed.
  • Delta Lake (in Databricks): use MERGE (upsert) and built-in versioning for CDC-like behavior.
Interview gold: Interviewers want efficiency thinking. Always contrast it with full load: "A full load reprocesses everything every night — slow and expensive. Incremental load uses a watermark to fetch only changed rows, so a 10-million-row table might only move a few thousand new rows per run."
Interview Q
"How do you implement incremental loading in ADF?"
Why they ask: the single most important real-world pipeline design question.
Walk through the watermark approach (the 5 steps above), mention the control table to persist state, and name CDC/Delta as alternatives. Bonus: mention handling late-arriving data with a staging area or tumbling-window reprocessing.

15. Slowly Changing Dimensions (SCD)

SCD is about how you handle changes to dimension data over time (like a customer changing their address). Two types come up most:

TypeWhat happens on changeHistory?
SCD Type 1Overwrite the old value with the new oneNo history kept
SCD Type 2Add a new row for the changed record; mark the old row inactive (with start/end dates or an "is current" flag)Full history kept

In ADF, you implement SCD using a Mapping Data Flow with the Alter Row transformation (to tag rows as insert/update/upsert) and a sink configured for upsert. Type 2 also uses a surrogate key and date columns.

One-line answer: "Type 1 overwrites and keeps no history; Type 2 inserts a new versioned row and preserves history with start/end dates. I implement them in Mapping Data Flows using Alter Row + upsert."

16. Error Handling & Debugging

Production pipelines are designed expecting failure, not hoping to avoid it. This shows production maturity.

Handling failures

  • Retry policies: set retry count + interval on activities for transient failures (use exponential backoff thinking).
  • Conditional paths: every activity has 4 output paths — Success, Failure, Completion, Skipped. Wire a Failure path to a logging/notification activity.
  • If Condition / Switch: branch logic based on results.
  • Alerts: integrate with Azure Monitor and Logic Apps to send email/Teams alerts on failure.
  • Logging & auditing: log every run and error to a table for audit trails.

Debugging

  • Use Debug runs to test before publishing.
  • Review each activity's output JSON for error details and metrics.
  • Check Self-Hosted IR logs for connectivity issues.
  • Use the Monitor hub to find the failed activity and map the error message to it.
Interview Tip: Mention the Failure vs Completion path difference — "Completion" runs whether the previous activity succeeded or failed (good for cleanup/logging), while "Failure" runs only on failure. Knowing this detail signals hands-on experience.

17. Monitoring

You monitor pipelines in the ADF Monitor hub, which shows pipeline runs, activity runs, trigger runs, statuses, durations, and error messages.

  • Pipeline/Activity runs: see what ran, when, how long, and pass/fail.
  • Alerts & metrics: set up alerts on failures or long runs via Azure Monitor.
  • Diagnostic logs: send logs to Log Analytics for KQL querying and dashboards.
  • Reruns: you can rerun a failed pipeline from the point of failure.

18. Performance Optimization

Interviewers test efficiency thinking — know why each tactic helps.

  • Incremental loads: move only changed data (biggest win).
  • Parallelism: tune Data Integration Units (DIUs) and degree of copy parallelism in Copy Activity to move data faster.
  • Partitioning: partition source/sink (e.g., by date) so reads aren't full-table scans, and ForEach can process partitions concurrently.
  • Right file formats: use columnar Parquet/ORC over CSV/JSON — smaller, faster, compressed.
  • Staging: use a Blob/ADLS staging area for big warehouse loads (PolyBase/COPY).
  • Break up big workflows: modular pipelines (Execute Pipeline) for reusability and parallelism.
DIU = Data Integration Unit — a measure of power (CPU/memory/network) ADF assigns to a Copy Activity. More DIUs = faster copy, but more cost. It's the main performance dial for Copy.

19. Cost Optimization

  • Avoid unnecessary runs: review trigger schedules; don't run hourly if daily is enough.
  • Right-size data movement: pick the right IR, region (keep compute near data), and DIU setting.
  • Shut down idle compute: especially a Self-Hosted IR running on a VM, and Data Flow clusters (set a short TTL).
  • Prefer Copy over Data Flow for simple moves (Data Flow spins up a Spark cluster = more cost).
  • Monitor with Azure Cost Management and set budgets/alerts.
How ADF billing works (good to mention): you're billed mainly by pipeline activity runs, data movement (DIU-hours), and Data Flow cluster time (vCore-hours). So fewer runs + less cluster time = lower bill.

20. Security & Key Vault

  • Managed Identity: let ADF authenticate to Azure services without passwords — the most secure option.
  • Azure Key Vault: store secrets, connection strings, and keys in Key Vault; ADF references them instead of hardcoding credentials.
  • RBAC: control who can view/edit/run ADF using role-based access (e.g., Data Factory Contributor).
  • Private Endpoints / Managed VNet: keep data traffic off the public internet; Managed VNet protects against data exfiltration.
  • Encryption: data is encrypted in transit (TLS) and at rest (AES).
Interview Tip: The phrase interviewers want to hear is "I store all secrets in Azure Key Vault and use Managed Identity for authentication" — it signals you never hardcode credentials.

21. CI/CD & Git Integration

ADF supports full CI/CD using Azure DevOps or GitHub.

  • Git integration: link ADF to a repo so all pipelines, datasets, and linked services are version-controlled. You work in feature branches.
  • Collaboration branch + publish: when you "Publish," ADF generates ARM templates into an adf_publish branch.
  • Deployment: a release pipeline in Azure DevOps deploys those ARM templates across environments (Dev → Test → Prod), overriding parameters per environment.
  • Why it matters: safe, repeatable, auditable deployments — no manual clicking in production.
Mode difference: In Git mode you "Save" to a branch (work-in-progress). "Publish" pushes the validated version live. Without Git, ADF is in "Live mode" and every change is immediately live — risky for teams.

22. ADF vs Synapse Pipelines / Databricks / SSIS

ToolWhat it's forvs ADF
ADFCloud data integration & orchestration (ETL/ELT)The orchestrator; 90+ connectors; light transformations
Synapse PipelinesSame engine as ADF, but inside Azure Synapse AnalyticsBest when your analytics already live in Synapse; fewer connectors than standalone ADF
Azure DatabricksHeavy data processing & ML on Apache Spark (code: Python/Scala/SQL)ADF orchestrates; Databricks does the heavy custom transformation. They're partners, not rivals.
SSISLegacy on-prem ETL tool (SQL Server Integration Services)ADF is the cloud-native successor; you can lift-and-shift SSIS into Azure-SSIS IR
Interview Tip: A very common question is "ADF vs Databricks." Best answer: "They complement each other — ADF orchestrates and moves data; Databricks does the heavy, code-based transformations. In real projects, ADF triggers a Databricks notebook for complex logic."
Bonus (2024+ awareness): Microsoft is pushing Microsoft Fabric, where "Data Factory" exists as a SaaS offering. Difference: standalone ADF is PaaS (you manage Integration Runtimes), while Fabric's Data Factory is SaaS (serverless managed compute, simplified "Connections," and Dataflow Gen2 with Power Query). Mentioning this shows you're current.

23. Important Limits (Interviewers Love These) ⭐

Knowing these real-world caveats instantly separates you from someone who only read theory:

ThingLimit / Rule
Lookup activity outputMax 5,000 rows or 2 MB
Get Metadata child itemsMax 8,000 items
ForEach itemsUp to 100,000 items; max 50 concurrent (parallel) iterations
Pipeline nesting (Execute Pipeline)Up to 20 levels deep
Pipeline timeoutDefault 7 days max
Tumbling Window concurrency1 per window (non-overlapping by design)
Real-time streamingADF is not true streaming — use Event triggers for near-real-time, or Event Hubs + Stream Analytics for true streaming
Where ADF metadata is storedInternally in Azure-managed storage (not user-visible)
The trap question: "Can ADF do real-time streaming?" — Say "No, not true streaming. ADF is batch/micro-batch. For near-real-time I use event-based triggers on file arrival; for true streaming I'd use Event Hubs + Azure Stream Analytics." Many candidates get this wrong.

24. Real Scenario-Based Questions

Scenario
"Copy all files from a Blob folder and load each filename + row count into a SQL table."
Approach: Use Get Metadata to list the folder's child items → ForEach to loop each file → inside, Get Metadata (or a Lookup) to get the row count → Copy/Stored Procedure to insert filename + count into SQL.
Scenario
"Your pipeline is slow during heavy loads. How do you optimize it?"
Approach: "Enable parallelism by partitioning data and raising DIUs/copy parallelism; switch to Parquet; use a Blob staging area to buffer; cache lookups in Data Flows; and move only incremental data instead of full reloads."
Scenario
"Migrate data from multiple cloud sources into an on-premises system."
Approach: "Use a Self-Hosted IR for the secure on-prem connection, define a Linked Service per source, and use Copy Activities (or a metadata-driven ForEach) to move each source into the on-prem target."
Scenario
"How would you design an end-to-end ADF pipeline?"
Approach (structured answer scores highest): Source identification → ingestion strategy (full vs incremental, batch vs event) → transformation approach (Data Flow vs Databricks) → error handling & retries → monitoring & alerting. Mention Key Vault for secrets and Git for CI/CD.
Scenario
"How do you handle late-arriving data?"
Approach: "Use time-window watermarking, land late data in a staging area, and reprocess specific partitions using tumbling window backfill or pipeline parameters with conditional branching."
Scenario
"Explain ADF to a non-technical stakeholder."
Approach: Use an analogy: "ADF is like a factory assembly line for data — it picks up raw data from many places, cleans and reshapes it on the line, and delivers finished, report-ready data to the business." Tests communication & simplification skill.
