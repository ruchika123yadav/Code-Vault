Azure data-platform map and service boundaries

A strong architecture answer assigns each service a clear responsibility instead of treating ADF, Databricks, Synapse, and Fabric as interchangeable.

Interview-ready answer

ADF primarily orchestrates and moves data, ADLS stores lake data, Event Hubs ingests event streams, Databricks performs scalable engineering and lakehouse processing, Azure SQL/Synapse/Fabric provide relational and analytical serving options, and Power BI provides semantic modeling and reporting.

Selection questions

  • Is the workload movement, transformation, orchestration, storage, or serving?
  • What freshness, volume, concurrency, and data-type requirements exist?
  • Which identity and network boundary controls access?
  • What is the durable replay point and idempotent target?
  • Who operates the service and how is cost attributed?
ADF vs Databricks?

ADF is strongest for orchestration, connectivity, and data movement; Databricks is strongest for code-first scalable transformation, streaming, and lakehouse workloads. They often work together rather than replacing each other.

Fabric vs separate Azure services?

Fabric offers an integrated SaaS analytics experience around OneLake and shared capacities. Separate Azure services can provide more independent service/network/compute choices. Select from governance, skills, workload isolation, migration, and operating model.

ADF pipeline, activity, dataset, and linked service

These four objects are foundational, and interviewers expect you to explain both their roles and how parameterization prevents duplication.

Interview-ready answer

An ADF pipeline is a logical workflow. An activity is one unit of work. A dataset describes the shape/location of data used by an activity, and a linked service contains connection information for a data store or compute service.

ObjectAnswersExample
PipelineWhich tasks and dependencies run?Lookup watermark -> Copy -> validate -> update watermark
ActivityWhat unit of work happens?Copy Activity or notebook execution
DatasetWhich data object/path/table is used?Parameterized ADLS Parquet path
Linked serviceHow do we connect/authenticate?Azure SQL endpoint using managed identity
Common confusion

A dataset is not the data itself, and a linked service should not be duplicated for every table. Reuse connections and parameterize datasets/pipelines where the contract is genuinely common.

Can one linked service serve many datasets?

Yes. A linked service represents the connection; multiple datasets can reference it for different tables, files, paths, or formats.

Where should a table name parameter live?

Often the pipeline receives the table metadata and passes it into a parameterized dataset. The exact placement depends on reuse, but parameters are immutable run inputs while variables are mutable pipeline state.

Azure and self-hosted Integration Runtime

Integration Runtime is the execution/connectivity bridge behind ADF data movement and activity dispatch. Network reachability determines the choice.

Interview-ready answer

Azure Integration Runtime provides managed cloud data movement and activity dispatch. Self-hosted Integration Runtime runs on a customer-managed machine or VM to reach private/on-premises networks. Azure-SSIS IR hosts SSIS package execution.

ScenarioChoiceReason
Azure Blob to ADLSAzure IRCloud endpoints with managed data movement
Private on-prem SQL ServerSelf-hosted IROutbound connection from a network that can reach source
Lift existing SSIS packagesAzure-SSIS IRManaged SSIS runtime
Security reasoning

A self-hosted IR normally initiates outbound connections, so inbound internet exposure is not the default requirement. Patch, monitor, size, and make the host highly available because it is your managed component.

Does self-hosted IR store business data permanently?

It is a data-movement runtime, not the target store. It can buffer data during movement, so host security, disk capacity, and cleanup still matter.

How do you improve self-hosted IR availability?

Add multiple nodes to the same runtime where supported, place them on reliable network paths, monitor resource/queue health, and avoid one under-sized workstation as a production dependency.

Copy, Mapping Data Flow, and control activities

Choose Copy Activity for movement, Mapping Data Flow for visual Spark transformations, and control activities to build reusable orchestration logic.

Interview-ready answer

Copy Activity moves data between supported sources and sinks with optional mappings and conversion. Mapping Data Flow performs visual, Spark-based transformations. Lookup/Get Metadata discover control information; ForEach iterates; If branches; Execute Pipeline composes reusable child pipelines.

NeedADF choiceWhy

ForEach scaling

Do not launch unlimited parallel copies against a source that cannot handle them. Set batch/concurrency from source limits, IR capacity, sink limits, and SLA.

Copy Activity vs Databricks transformation?

Use Copy for movement and lightweight mapping. Use Databricks when transformations need code, complex Spark logic, streaming, Delta operations, reusable libraries, or deep performance control.

Lookup vs Get Metadata?

Lookup reads rows or a result set from supported data; Get Metadata reads properties of a dataset such as file existence, size, modified time, or child items.

Parameters, variables, expressions, and metadata-driven ADF

Metadata-driven design scales repeated patterns while keeping table-specific contracts visible and governable.

Interview-ready answer

ADF parameters are immutable inputs supplied to a pipeline, dataset, linked service, or data flow. Variables are mutable values within a pipeline run. Dynamic expressions combine parameters, activity output, system variables, and functions at run time.

JSON - control table example
{
  "source_table": "sales.orders",
  "sink_path": "bronze/orders",
  "load_type": "watermark",
  "watermark_column": "updated_at",
  "business_key": ["order_id"],
  "parallel_copies": 4,
  "quality_profile": "orders_v2",
  "enabled": true
}
ADF expression examples
@pipeline().parameters.sourceTable
@activity('LookupConfig').output.value
@concat(pipeline().parameters.basePath, '/', item().sink_path)
@formatDateTime(pipeline().TriggerTime, 'yyyy/MM/dd/HH')

Metadata framework layers

  1. Parent reads enabled configurations.
  2. ForEach calls a reusable child with one config.
  3. Child selects full/watermark/CDC behavior.
  4. Audit table records range, counts, status, error, and version.
  5. Only successful reconciled runs advance state.
Dynamic SQL trap

Parameterization does not make arbitrary table or column input safe. Control metadata must be validated/allow-listed, and data values should use connector query parameters where possible.

Parameters vs variables?

Parameters define immutable run inputs and support reuse; variables change during execution. Avoid variables for parallel ForEach state unless race behavior is deliberately controlled.

What should not be generic?

Do not hide unique business transformations, keys, delete semantics, or quality rules behind an overly generic copy framework. Parameterize repeatable mechanics and keep contracts explicit.

ADF triggers and incremental watermark pipeline

Scheduling and incremental state must be designed together. Trigger time is not automatically the data interval or watermark.

Interview-ready answer

A schedule trigger fires on a calendar schedule, a tumbling-window trigger represents contiguous stateful time windows with dependency/retry support, and an event trigger reacts to supported storage events. A watermark pipeline reads a stable old-to-new boundary and advances state only after successful target publication.

Watermark activity flow

Lookup oldLast committed value
->
Lookup newStable source high value
->
Copy rangeold < x <= new
->
ValidateCounts + quality
->
Commit stateOnly after success
SQL - source range
SELECT *
FROM dbo.orders
WHERE (updated_at > @old_watermark)
  AND (updated_at <= @new_watermark);
Tie and delete trap

If multiple rows share timestamp precision, use a composite boundary or overlapping read plus deduplication. A timestamp watermark normally captures inserts/updates, not hard deletes.

Schedule vs tumbling-window trigger?

Use schedule for simple periodic starts. Use tumbling windows when runs represent contiguous time slices and you need state, retry, concurrency, or dependency between windows.

Why update the watermark last?

Advancing it before target success can skip data after failure. Advancing last may replay a successful write if state update fails, so the target must be idempotent.

ADF retries, failure paths, schema drift, and monitoring

Production ADF design separates transient retries, record-level rejects, contract failures, and business-quality failures.

Interview-ready answer

I configure bounded retries for transient activity failures, explicit success/failure dependencies, structured audit logging, and actionable alerts. I treat schema drift as a policy decision: compatible approved changes may flow; breaking or unknown changes are quarantined or fail the pipeline.

FailureResponseEvidence
Timeout/throttlingRetry with delay; alert after budgetRetry count and final error
Bad row in supported copyFault-tolerant skip/quarantine if policy allowsRejected count and file/log
Breaking schemaStop affected contractExpected vs observed schema
Quality/reconciliation gapDo not publish/advance stateRule and count/amount difference

Useful monitoring fields

Pipeline/activity run IDs, trigger, parameter set, source range, IR, rows/bytes read and written, throughput, duration, queue time, retries, files skipped, error code, and user properties that identify dataset/table.

How do you rerun only a failed table in a metadata pipeline?

Persist per-table run state and source boundary, then invoke the child pipeline for that configuration/range. Do not rerun successful tables if doing so creates unnecessary source load or duplicate risk.

Would you skip every incompatible row?

No. Skip/quarantine only known record-level defects within an agreed threshold. A systemic schema or mapping error should fail because most output could be wrong.

ADLS Gen2, hierarchical namespace, and lake layout

ADLS Gen2 combines Blob Storage capabilities with hierarchical namespace semantics useful for analytics paths and directory-level operations.

Interview-ready answer

ADLS Gen2 is Azure Blob Storage with hierarchical namespace enabled, organizing objects as directories and files and supporting directory-level operations and POSIX-style ACLs. I design paths from data ownership, layer, dataset, and useful partition filters, not from an arbitrary folder tree.

Path convention
abfss://raw@account.dfs.core.windows.net/commerce/orders/
  ingest_date=2026-07-23/hour=10/part-0001.json

abfss://curated@account.dfs.core.windows.net/commerce/orders_silver/
  event_date=2026-07-22/part-0001.parquet

Design choices

  • Separate security/ownership boundaries with accounts or containers only when needed.
  • Use dataset-oriented directories and partition columns used by queries.
  • Keep checkpoint/schema/control paths distinct from business data.
  • Apply lifecycle tiers/deletion from access pattern and retention obligations.
  • Avoid secrets and PII in object names because names appear in logs and listings.
Why enable hierarchical namespace?

It provides real directory semantics, efficient directory rename/delete behavior, and ACLs that align with analytics engines. The choice should be made at account creation with feature compatibility considered.

Should Bronze be partitioned by event date or ingestion date?

Ingestion date is dependable for operational replay and arrival tracking; event date supports event-time queries but can be late or invalid. Many designs retain ingestion organization in Bronze and event-date organization in curated layers.

RBAC, ACLs, managed identity, service principals, and Key Vault

Authentication proves identity; authorization grants actions; network controls determine reachability. Secure architecture needs all three.

Interview-ready answer

Azure RBAC grants management or data-plane roles at Azure resource scopes. ADLS ACLs grant directory/file permissions and require execute permission to traverse parent directories. A managed identity is an Azure-managed service identity; a service principal is an application identity whose credential lifecycle you manage. Key Vault protects secrets, keys, and certificates.

NeedPreferred controlReason
ADF reads one ADLS containerADF managed identity + least data role/ACLNo stored client secret
Fine directory accessPOSIX ACL plus parent traversalPath-level restriction
External automation identityService principal/certificate or federationNon-human application principal
Legacy secret neededKey Vault reference + rotationCentralized access/audit
Secret-zero problem

Putting a Key Vault secret name in configuration is fine; putting the vault credential in the same configuration defeats the design. Use managed identity or another credential-free/federated bootstrap where possible.

RBAC vs ACL in ADLS?

RBAC applies at Azure scopes such as account/container and is simpler for broad access. ACLs provide fine-grained directory/file permissions. Effective access can involve both models, so test with the actual identity.

System-assigned vs user-assigned managed identity?

A system-assigned identity is tied to one resource lifecycle. A user-assigned identity is a separate reusable Azure resource that can be attached to multiple services and managed independently.

Azure SQL and Synapse serverless vs dedicated SQL

Azure SQL is a managed relational database family; Synapse SQL adds distributed analytical choices for querying lake files or reserved warehouse compute.

Interview-ready answer

Azure SQL Database is a managed relational database suited to operational and serving workloads. Synapse serverless SQL queries supported lake data in place with automatically managed compute and pay-per-data-processed behavior. Dedicated SQL pool uses provisioned distributed compute and stored/distributed tables for predictable warehouse workloads.

RequirementLikely choiceReason
Application transactionsAzure SQL DatabaseOLTP and relational constraints
Occasional exploration of Parquet in ADLSSynapse serverlessQuery in place without reserved warehouse

T-SQL - serverless Parquet query
SELECT event_date, SUM(amount) AS revenue
FROM OPENROWSET(
    BULK 'https://account.dfs.core.windows.net/gold/orders/**',
    FORMAT = 'PARQUET'
) WITH (
    event_date date,
    amount decimal(18,2)
) AS rows
WHERE event_date >= '2026-07-01'
GROUP BY event_date;

Performance and security anchors

Use least-privilege Entra identities, private connectivity/firewall controls, indexes and query plans for Azure SQL, and partition/file pruning for serverless. Dedicated pools additionally require good table distribution to reduce data movement.

Why can serverless SQL become expensive?

It charges based on data processed, so repeated broad scans, poor file formats, missing partition filters, and too many tiny files increase both latency and cost.

Hash vs replicated table in a dedicated pool?

Hash-distribute large tables on a well-distributed join key to colocate work. Replicate small dimensions to each compute node to avoid data movement. Validate skew and query patterns.

Event Hubs namespace, hub, partitions, and consumer groups

Event Hubs is a managed event-ingestion service. Correct design centers on partition key, capacity, retention, and independent consumer progress.

Interview-ready answer

An Event Hubs namespace is the management and capacity boundary, an event hub is the event stream, partitions are ordered logs used for parallelism, and consumer groups provide independent views/progress for separate consuming applications.

PublishersEvents + partition key
->
Event hubPartitioned retained log
->
Consumer groupsFraud / lake / dashboard

Partition key

Use order_id when order-event ordering matters. Events with the same key are routed together, but a hot key can overload one partition. Without a key, distribution improves but entity ordering is not guaranteed.

Can two applications share a consumer group?

They can, but processors in the same group compete for partition ownership and split the stream. Independent applications that each need every event should use separate consumer groups.

How do you estimate partition needs?

Use peak event/byte rate, required processing parallelism, key distribution, service-tier limits, consumer throughput, and growth. Partitions define ordering and cannot be treated as a free tuning knob.

Event Hubs checkpoints, Capture, Kafka endpoint, and notifications

Checkpointing tracks consumer progress; Capture archives the stream to storage. Neither replaces event-time watermarks or business deduplication.

Interview-ready answer

An Event Hubs consumer checkpoint stores the last processed position per partition so processing can resume. Event Hubs Capture automatically writes event batches to Blob/ADLS for durable archive. The Kafka endpoint lets compatible Kafka clients use Event Hubs without running Kafka brokers.

ConceptPurposeNot the same as
CheckpointConsumer recovery positionLate-event watermark
CaptureManaged archive to storage windowsCurated/validated Bronze table
Consumer groupIndependent consumption viewSecurity group
Logic Apps alertWorkflow/notification after a signalPrimary metrics/log store
Checkpoint timing

Checkpoint only after durable business output. If you checkpoint first, a crash can lose events; if you checkpoint after, replay is possible and the sink must be idempotent.

Capture vs a streaming consumer writing Bronze?

Capture is a low-operations archival path with time/size windows. A streaming consumer can validate, enrich metadata, control file/table format, and produce lower-latency structured Bronze, but it requires compute and checkpoint operations.

Where should Logic Apps fit?

Use it after an Azure Monitor alert or pipeline failure event to route notifications/tickets with context. Do not make alert delivery the only evidence; keep durable logs and alert state.

Delta transaction log, ACID, time travel, MERGE, and CDF

Delta adds table-level reliability and history around data files. Interview depth includes conflict behavior, deterministic merge, and replay boundaries.

Interview-ready answer

A Delta table stores data files plus a transaction log containing ordered table actions and metadata. Optimistic concurrency and atomic commits provide ACID table behavior, time travel reads prior versions, MERGE applies matched/unmatched changes, and Change Data Feed exposes row-level changes between versions when enabled.

SQL - deterministic Delta merge
MERGE INTO silver.customer AS t
USING staged_customer AS s
ON t.customer_id = s.customer_id
WHEN MATCHED AND s.sequence_no > t.sequence_no THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;

Important distinctions

  • Time travel uses retained transaction history/files; retention cleanup can remove old versions.
  • CDF gives changes produced by a Delta table; it is not automatically the original source-database CDC log.
  • MERGE is only deterministic when one winning source row exists per target key and sequence rules are explicit.
  • ACID protects table commits; cross-table business transactions need separate design.
Multiple-match trap

Deduplicate source changes to one deterministic winner per target key or use logic that intentionally handles ordered events. Multiple ambiguous source matches can fail or produce incorrect updates.

How does optimistic concurrency work?

A writer reads a table snapshot, prepares changes, then validates at commit that conflicting actions have not invalidated its assumptions. Non-conflicting commits can succeed; conflicts are retried or resolved.

Time travel vs backup?

Time travel is convenient table-version access within retained history, not a complete independent disaster-recovery strategy. Retention, accidental deletion, account failure, and external dependencies still require backup/DR planning.

Delta schema evolution, compaction, OPTIMIZE, Z-ORDER, and VACUUM

Optimization changes physical layout and retention, so it must follow measured query patterns and recovery requirements.

Interview-ready answer

Schema enforcement rejects incompatible writes by default; controlled evolution accepts approved compatible changes. OPTIMIZE compacts small files, Z-ORDER can colocate values to improve data skipping for selected columns, and VACUUM removes old unreferenced files after the retention period.

OperationSolvesDoes not solve
OPTIMIZE/compactionSmall-file overheadBad business grain or duplicates
Z-ORDERSkipping for selective filtersEvery possible query pattern
VACUUMStorage from obsolete filesImmediate logical row deletion alone

VACUUM trap

Reducing retention aggressively can break readers/jobs using old snapshots and remove time-travel/recovery options. Align retention with maximum job duration, replay, and governance requirements.

When would you use Z-ORDER?

For frequently filtered high-value columns where file-level clustering improves skipping, after confirming scan behavior. Avoid blindly Z-Ordering every column because optimization has compute cost.

What is predictive optimization?

For supported Unity Catalog managed tables, Databricks can automatically run maintenance such as optimization based on observed needs. Know current scope and still monitor workload outcomes.

Auto Loader checkpoints and schema location

Auto Loader incrementally discovers cloud files. Checkpoint and schema location solve different state problems and should not be shared carelessly.

Interview-ready answer

Databricks Auto Loader uses the cloudFiles source to incrementally discover and process new files from cloud object storage. The streaming checkpoint tracks query progress and state; the schema location stores inferred schema and schema-evolution metadata.

PySpark - Auto Loader
raw = (
    spark.readStream
         .format("cloudFiles")
         .option("cloudFiles.format", "json")
         .option("cloudFiles.schemaLocation", "/control/orders_schema")
         .option("cloudFiles.schemaEvolutionMode", "addNewColumns")
         .load("/landing/orders")
)

query = (
    raw.writeStream
       .format("delta")
       .option("checkpointLocation", "/checkpoints/orders_bronze")
       .trigger(availableNow=True)
       .toTable("bronze.orders")
)

Production design

  • One logical query has its own reliable checkpoint.
  • Schema location is separate from checkpoint and data output.
  • Rescued/unexpected data is retained and monitored.
  • Source file identity and ingestion metadata are preserved.
  • Duplicate file/content behavior is tested.
  • Schema changes follow a contract, not unlimited auto-merge.
What happens if you delete the checkpoint?

The query loses its recorded progress and may rediscover/reprocess files. Target idempotency becomes critical, and stateful query compatibility must be considered before resetting.

Auto Loader vs ADF Copy?

Lakeflow Declarative Pipelines and Expectations

Lakeflow Spark Declarative Pipelines, formerly DLT, lets you declare datasets and quality behavior while the platform manages dependency execution and operational metadata.

Interview-ready answer

Lakeflow Spark Declarative Pipelines is a framework for defining batch and streaming data pipelines as tables, views, and flows with managed dependency orchestration. Expectations declare data-quality rules and whether violations are monitored, dropped, or fail an update.

Python - declarative pipeline pattern
from pyspark import pipelines as dp
from pyspark.sql import functions as F

@dp.table(name="orders_bronze")
def orders_bronze():
    return (
        spark.readStream.format("cloudFiles")
             .option("cloudFiles.format", "json")
             .load("/landing/orders")
    )

@dp.table(name="orders_silver")
@dp.expect_or_drop("valid_order_id", "order_id IS NOT NULL")
@dp.expect_or_fail("valid_amount", "amount >= 0")
def orders_silver():
    return spark.readStream.table("orders_bronze").select(
        "order_id", "customer_id", "event_time", "amount"
    )

AUTO CDC, sequence keys, and SCD Type 2

AUTO CDC simplifies ordered change application, but correctness still depends on source operation semantics, business keys, and sequence ordering.

Interview-ready answer

AUTO CDC APIs apply source change events to a target using declared keys, sequence ordering, operation rules, and SCD type. For SCD Type 2, the sequence must order versions correctly so out-of-order arrival does not corrupt effective history.

Python - conceptual AUTO CDC flow
from pyspark import pipelines as dp
from pyspark.sql.functions import col, struct

dp.create_streaming_table("customer_scd2")

dp.create_auto_cdc_flow(
    target="customer_scd2",
    source="customer_changes",
    keys=["customer_id"],
    sequence_by=struct(col("event_ts"), col("source_sequence")),
    apply_as_deletes=col("operation") == "DELETE",
    except_column_list=["operation"],
    stored_as_scd_type=2,
)

Input contract

  • Stable business key.
  • Operation semantics for insert/update/delete.
  • Monotonic or deterministic sequence per key.
  • Columns excluded from target business state.
  • Policy for null updates, truncates, and snapshots.
Timestamp trap

Do not assume ingestion timestamp is a correct sequence. Delayed source events can arrive later with an older business version. Prefer database log sequence/version or a composite deterministic ordering field.

AUTO CDC vs MERGE?

MERGE is a general row matching/upsert command that you orchestrate. AUTO CDC provides declarative ordered CDC application and SCD handling in Lakeflow pipelines. Both require correct keys and source semantics.

Can watermark-based updates feed AUTO CDC?

They can feed an upsert-style stream if you construct a correct sequence and operation contract, but if hard deletes are absent it is not full CDC. Say that limitation explicitly.

Power BI semantic models, DAX, refresh, gateway, and RLS

Data engineers should understand how Gold data becomes a usable semantic model and why relationships, measure context, and security affect report correctness.

Interview-ready answer

A Power BI semantic model defines tables, relationships, measures, hierarchies, formats, and security for business analysis. Measures are evaluated in filter context at query time; calculated columns are materialized row by row during refresh. CALCULATE evaluates an expression under modified filter context.

DAX - core measures
Total Revenue = SUM(FactSales[Revenue])

Revenue Previous Year =
CALCULATE(
    [Total Revenue],
    SAMEPERIODLASTYEAR(DimDate[Date])
)

Customer Revenue =
CALCULATE(
    [Total Revenue],
    KEEPFILTERS(DimCustomer[IsActive] = TRUE())
)

Model rules

  • Prefer a star with one-to-many dimension-to-fact relationships.
  • Use single filter direction unless a proven many-to-many scenario needs more.
  • Avoid ambiguous paths and uncontrolled bidirectional filtering.
  • Use measures for aggregations that respond to report filters.
  • Use a gateway when the service must securely reach supported on-premises sources.
  • Test RLS using real role/user mapping and remember workspace roles can affect behavior.
Measure vs calculated column?

A calculated column is computed per row during refresh and stored, increasing model size. A measure is computed at query time in filter context and is usually appropriate for aggregations.

What is filter context?

It is the set of filters applied by visuals, slicers, relationships, and DAX. CALCULATE can add, replace, or preserve filters while evaluating an expression.

Checkpoint vs watermark in this project?

The checkpoint stored streaming progress and state for recovery. The watermark bounded event-time state and defined late-event handling. They solve different problems and both were required.

How did restart work?

The stream reused its durable checkpoint and resumed source positions. Bronze/Silver writes were transactional/idempotent, event IDs/versions neutralized replay, and quality/reconciliation metrics confirmed recovery.

Customer/driver changes used business keys and a trustworthy sequence column; ordered changes created effective-dated versions with one current row. Deletes and out-of-order events followed explicit source-operation rules.

Resume defense: Spotify-style batch/lakehouse project

This defense focuses on Azure SQL incremental ingestion, truthful CDC wording, Auto Loader placement, Unity Catalog access, SCD2, deployment, and monitoring.

Two-minute architecture answer

Interview-ready answer

ADF extracted bounded incremental ranges from Azure SQL into an ADLS landing/Bronze area. Auto Loader incrementally discovered the landed files into Delta, Lakeflow pipelines applied quality and modeled Silver/Gold tables, Unity Catalog governed tables and storage access through managed identity, Bundles deployed versioned resources, and Azure Monitor/Logic Apps routed operational alerts.

Watermark state contract

SQL - composite incremental range
SELECT *
FROM dbo.tracks
WHERE updated_at > @old_ts
   OR (updated_at = @old_ts AND track_id > @old_track_id)
  AND (
       updated_at < @new_ts
       OR (updated_at = @new_ts AND track_id <= @new_track_id)
  );

Store dataset, old/new timestamp, tie-breaker key, run ID, status, source/target counts, and commit time in a control table. Commit the new boundary only after target write and reconciliation succeed.

CDC wording

A last-modified watermark captures inserts/updates that change the column. It is not full CDC when hard deletes are absent. Say watermark-based incremental ingestion unless a real change log/tracking mechanism captured operations.

Why Auto Loader after ADF already copied files?

ADF handled source connectivity, bounded extraction, and landing. Auto Loader efficiently and incrementally discovered those cloud files inside Databricks and integrated their progress/schema state with the streaming Delta pipeline.

How did managed identity reach ADLS through Unity Catalog?

An Azure Databricks access connector or supported managed identity received least storage permissions. Unity Catalog represented it as a storage credential, bound it to an external location, and granted users/services UC privileges rather than raw cloud credentials.

How did Logic Apps monitoring work?

ADF/Databricks diagnostics and run signals fed Azure Monitor/Log Analytics; an alert or failure event triggered an action group/Logic Apps workflow that sent a contextual notification or ticket. Durable run logs remained the source for investigation.

What would happen to deletes?

If only the timestamp watermark existed, hard deletes would be missed. I would use SQL Change Tracking/CDC, soft-delete flags, periodic anti-join reconciliation, or a source deletion feed based on source capability and SLA.
